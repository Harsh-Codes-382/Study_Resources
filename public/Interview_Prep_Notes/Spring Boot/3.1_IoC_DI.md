# 3.1 IoC / DI — Spring Interview Preparation

## 1. IoC — Inversion of Control

### Definition

**IoC (Inversion of Control)** means that instead of application classes controlling the creation and wiring of their dependencies, the **Spring container takes responsibility for object creation, dependency wiring, and lifecycle management**.

Without Spring:

```java
class OrderService {

    private PaymentService paymentService;

    public OrderService() {
        this.paymentService = new PaymentService();
    }
}
```

Here `OrderService` controls the creation of `PaymentService`.

With Spring:

```java
class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

`OrderService` only declares:

> "I need a `PaymentService`."

Spring creates the dependency and supplies it.

Conceptually:

```text
Without Spring:

OrderService
    |
    └── creates PaymentService


With Spring:

             Spring Container
                    |
             creates PaymentService
                    |
                    ↓
              OrderService
                    |
                    ↓
             PaymentService
```

### What exactly is inverted?

The **control over object creation and dependency wiring** is inverted.

Instead of:

```text
Class → creates dependency
```

we have:

```text
Spring Container → creates and wires dependency → Class
```

### Interview answer

> IoC means that instead of application classes controlling the creation and wiring of their dependencies, the Spring container takes that responsibility. The class declares what it needs, and the container provides it.

---

# 2. IoC Container

The Spring IoC container is responsible for:

- creating objects
- managing objects
- injecting dependencies
- managing bean lifecycle
- managing bean scopes
- processing configuration

Objects managed by Spring are called **beans**.

Conceptually:

```text
Spring Container
│
├── PaymentService bean
├── OrderService bean
├── UserService bean
└── EmailService bean
```

---

# 3. `ApplicationContext`

`ApplicationContext` is the main Spring IoC container used in modern Spring/Spring Boot applications.

Example:

```java
ApplicationContext context =
        new AnnotationConfigApplicationContext(AppConfig.class);
```

A bean can technically be retrieved with:

```java
PaymentService service =
        context.getBean(PaymentService.class);
```

However, normal Spring application code usually does not manually call `getBean()`.

Instead, dependencies are injected:

```java
@Service
class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Spring handles the wiring.

---

# 4. `ApplicationContext` vs `BeanFactory`

Both are Spring IoC containers.

## `BeanFactory`

`BeanFactory` provides the basic IoC/DI functionality.

It is the older, lower-level container abstraction.

```text
BeanFactory
    ↓
Basic IoC functionality
```

## `ApplicationContext`

`ApplicationContext` builds on the basic bean factory functionality and provides additional application-level features such as:

- application events
- internationalization/message resolution
- resource loading
- bean post-processing integration
- easier integration with Spring's broader infrastructure

Conceptually:

```text
ApplicationContext
       ↓
   BeanFactory
       +
   additional
   application
   features
```

### Interview answer

> `BeanFactory` provides the basic IoC container functionality, while `ApplicationContext` extends that functionality with features such as event publishing, message resolution, resource loading, and integration with Spring's bean post-processing infrastructure. Spring Boot applications generally use `ApplicationContext`.

# 5. Dependency Injection — DI

**Dependency Injection (DI)** is one of the main ways Spring implements IoC.

Suppose:

```java
class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

`OrderService` depends on:

```java
PaymentService
```

Instead of doing:

```java
new PaymentService()
```

inside `OrderService`, Spring supplies the dependency.

That is Dependency Injection.

### Simple mental model

```text
IoC
 ↓
Spring controls object creation/wiring

DI
 ↓
Spring supplies dependencies to objects
```

---

# 6. Types of Dependency Injection

Spring supports three common forms:

1. Constructor injection
2. Setter injection
3. Field injection

---

# 7. Constructor Injection

Example:

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Conceptually, Spring performs something like:

```java
PaymentService paymentService =
        /* get/create managed bean */;

OrderService orderService =
        new OrderService(paymentService);
```

## Why constructor injection is preferred

### 7.1 Dependencies can be `final`

```java
private final PaymentService paymentService;
```

The dependency must be supplied during construction and cannot be replaced afterward.

This makes the class safer and communicates that the dependency is required.

---

### 7.2 Dependencies are explicit

Look at:

```java
public OrderService(PaymentService paymentService) {
    this.paymentService = paymentService;
}
```

Anyone looking at the constructor immediately knows:

> OrderService requires PaymentService.

The dependency is not hidden.

---

### 7.3 Better testability

Constructor injection makes unit testing easy.

```java
PaymentService mockPaymentService =
        mock(PaymentService.class);

OrderService service =
        new OrderService(mockPaymentService);
```

No Spring container is required just to construct the class.

This is especially useful for unit tests.

---

### 7.4 Avoids hidden null dependencies

With constructor injection:

```java
OrderService(PaymentService paymentService)
```

the required dependency has to be supplied when the object is created.

With field injection:

```java
@Autowired
private PaymentService paymentService;
```

an object can exist before Spring performs injection.

For example, outside the Spring container:

```java
OrderService service = new OrderService();
```

`paymentService` would not automatically be injected.

---

### 7.5 Helps expose circular dependencies

Consider:

```java
class A {
    A(B b) {}
}

class B {
    B(A a) {}
}
```

To create A, Spring needs B.

To create B, Spring needs A.

There is no valid construction order.

Constructor injection therefore exposes the circular dependency during bean creation.

---

# 8. Setter Injection

Example:

```java
@Service
public class OrderService {

    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(
            PaymentService paymentService) {

        this.paymentService = paymentService;
    }
}
```

Conceptually:

```text
1. Create OrderService
2. Call setPaymentService(...)
3. Dependency is injected
```

Setter injection can make sense when a dependency is:

- optional
- configurable after construction
- genuinely changeable

For mandatory dependencies, constructor injection is normally preferred.

---

# 9. Field Injection

Example:

```java
@Service
public class OrderService {

    @Autowired
    private PaymentService paymentService;
}
```

Conceptually:

```text
Create OrderService
       ↓
Spring injects field
       ↓
paymentService becomes available
```

## Problems with field injection

### 9.1 Dependencies are hidden

Looking only at:

```java
OrderService service = new OrderService();
```

you cannot see that the class requires `PaymentService`.

---

### 9.2 Harder to unit test

You cannot naturally do:

```java
new OrderService(mockPaymentService);
```

because there is no constructor accepting the dependency.

You often need Spring or reflection-based techniques to inject the field.

---

### 9.3 Required dependencies cannot naturally be `final`

With constructor injection:

```java
private final PaymentService paymentService;
```

With field injection, the field is normally not final because Spring injects it after construction.

---

### 9.4 Object can exist before dependencies are injected

This makes the dependency lifecycle less explicit.

### Interview answer

> Constructor injection is preferred because dependencies are explicit, required dependencies can be stored in final fields, unit testing is easier, and constructor cycles are detected during bean creation.

# 10. Declaring Spring Beans

There are two major approaches:

1. Component scanning with stereotypes such as `@Component`, `@Service`, `@Repository`
2. Explicit bean definitions using `@Bean`

---

# 11. `@Component` and Stereotype Annotations

Example:

```java
@Component
public class PaymentService {
}
```

Spring's component scanning can discover this class and register it as a bean.

Common stereotype annotations include:

```java
@Component
@Service
@Repository
@Controller
@RestController
```

## `@Service`

```java
@Service
public class OrderService {
}
```

Usually used for business/service logic.

## `@Repository`

```java
@Repository
public class OrderRepository {
}
```

Used for persistence/data-access classes.

## `@Controller`

Used for Spring MVC controllers.

## `@RestController`

Used for REST controllers.

These annotations communicate the intended role of the class.

---

# 12. `@Bean`

`@Bean` is used to explicitly declare a bean.

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}
```

Here:

```java
paymentService()
```

returns an object that Spring registers as a bean.

Think:

```text
@Component
    ↓
"Spring, discover and manage this class."

@Bean
    ↓
"Spring, manage the object returned by this method."
```

---

# 13. When is `@Bean` useful?

`@Bean` is especially useful when:

- you need custom construction logic
- you need to configure an object
- the class is from a third-party library
- you cannot modify the class to add `@Component`

For example, suppose:

```java
SomeThirdPartyClient
```

comes from an external library.

You cannot normally modify that class and add:

```java
@Component
```

Instead:

```java
@Configuration
public class AppConfig {

    @Bean
    public SomeThirdPartyClient client() {
        return new SomeThirdPartyClient(
                "https://api.example.com"
        );
    }
}
```

Now Spring manages that client.

---

# 14. Is `@Bean` Only Allowed Under `@Configuration`?

**No.**

A `@Bean` method can also exist in another Spring-managed component.

For example:

```java
@Component
public class MyConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}
```

Spring can process the `@Bean` method because `MyConfig` itself is a Spring-managed component.

However, there is an important distinction.

## `@Configuration`

```java
@Configuration
class AppConfig {

    @Bean
    A a() {
        return new A();
    }
}
```

provides **full configuration-class semantics**.

A regular component containing `@Bean` methods has **lite configuration semantics**.

Therefore, the normal and recommended pattern is:

```java
@Configuration
class AppConfig {

    @Bean
    ...
}
```

### Important interview statement

> `@Bean` is not restricted to `@Configuration` classes, but `@Configuration` is the standard approach for declaring bean definitions because it provides full configuration-class semantics.

---

# 15. What Is `@Configuration`?

`@Configuration` tells Spring:

> "This class contains configuration information, especially bean definitions."

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}
```

Spring sees:

```text
AppConfig
   ↓
@Configuration
   ↓
Configuration class
   ↓
Process @Bean methods
   ↓
Register returned objects as beans
```

---

# 16. `@Configuration` Is a Specialized Component

Conceptually:

```text
@Configuration
      ↓
specialized Spring component
```

A configuration class itself is also registered with Spring, but it has additional configuration semantics.

Compare:

```java
@Component
public class EmailService {
}
```

This means:

> "Manage this class as a bean."

While:

```java
@Configuration
public class AppConfig {
}
```

means:

> "Manage this class as configuration and process its bean definitions."

---

# 17. Why `@Configuration` Matters with Multiple `@Bean` Methods

Consider:

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }

    @Bean
    public OrderService orderService() {
        return new OrderService(paymentService());
    }
}
```

At first glance, you might think:

```java
paymentService()
```

simply creates:

```java
new PaymentService()
```

every time it is called.

But with full `@Configuration` semantics, Spring can intercept calls between `@Bean` methods and return the container-managed bean.

Conceptually:

```text
ApplicationContext
      │
      ├── PaymentService → instance A
      │
      └── OrderService
               │
               └── PaymentService → instance A
```

Therefore, the same managed singleton bean can be reused.

---

# 18. `@Configuration` vs `@Component` + `@Bean`

### `@Configuration`

```java
@Configuration
class AppConfig {

    @Bean
    A a() {
        return new A();
    }

    @Bean
    B b() {
        return new B(a());
    }
}
```

Provides full configuration semantics.

### Regular `@Component`

```java
@Component
class AppConfig {

    @Bean
    A a() {
        return new A();
    }

    @Bean
    B b() {
        return new B(a());
    }
}
```

This is a valid Spring-managed component containing `@Bean` methods, but it has **lite configuration semantics**.

Direct Java calls between its `@Bean` methods behave like ordinary method calls rather than receiving the same full configuration-class interception.

Therefore:

```text
@Configuration + @Bean
        ↓
Recommended for configuration classes

@Component + @Bean
        ↓
Possible, but lite semantics
```

# 19. Resolving Bean Ambiguity

Suppose:

```java
interface PaymentService {
    void pay();
}
```

and there are two implementations:

```java
@Service
class StripePaymentService
        implements PaymentService {
}
```

```java
@Service
class RazorpayPaymentService
        implements PaymentService {
}
```

Now:

```java
@Service
class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Spring sees:

```text
PaymentService
      │
      ├── StripePaymentService
      │
      └── RazorpayPaymentService
```

There are two matching candidates.

Spring cannot simply choose randomly.

Common ways to resolve this are:

- `@Primary`
- `@Qualifier`

---

# 20. `@Primary`

Mark one bean as the preferred/default candidate:

```java
@Service
@Primary
class StripePaymentService
        implements PaymentService {
}
```

Now:

```java
PaymentService paymentService
```

will normally resolve to:

```text
StripePaymentService
```

because it is marked `@Primary`.

### Mental model

```text
@Primary
   ↓
"If nobody specifies otherwise, prefer me."
```

---

# 21. `@Qualifier`

`@Qualifier` explicitly identifies which bean should be injected.

Example:

```java
@Service("stripe")
class StripePaymentService
        implements PaymentService {
}
```

```java
@Service("razorpay")
class RazorpayPaymentService
        implements PaymentService {
}
```

Then:

```java
@Service
class OrderService {

    private final PaymentService paymentService;

    public OrderService(
            @Qualifier("razorpay")
            PaymentService paymentService) {

        this.paymentService = paymentService;
    }
}
```

Spring selects:

```text
@Qualifier("razorpay")
        ↓
RazorpayPaymentService
```

### Mental model

```text
@Qualifier
    ↓
"For this injection, use this specific bean."
```

---

# 22. `@Primary` vs `@Qualifier`

### `@Primary`

Defines the preferred/default candidate.

```java
@Primary
class StripePaymentService
```

### `@Qualifier`

Explicitly selects a particular candidate.

```java
@Qualifier("razorpay")
PaymentService paymentService
```

If both exist:

```text
PaymentService
├── StripePaymentService @Primary
└── RazorpayPaymentService
```

Then:

```java
PaymentService service
```

→ Stripe.

But:

```java
@Qualifier("razorpay")
PaymentService service
```

→ Razorpay.

---

# 23. Injecting All Beans with `List<T>`

Sometimes you don't want one implementation.

You want all implementations.

Example:

```java
@Service
class PaymentProcessor {

    private final List<PaymentService> services;

    public PaymentProcessor(
            List<PaymentService> services) {

        this.services = services;
    }
}
```

If Spring has:

```text
StripePaymentService
RazorpayPaymentService
PayPalPaymentService
```

Spring can inject:

```text
[
    StripePaymentService,
    RazorpayPaymentService,
    PayPalPaymentService
]
```

This is useful for:

- strategy patterns
- plugin-like architectures
- running multiple implementations
- processing all handlers

---

# 24. Injecting All Beans with `Map<String, T>`

Spring can also inject a map:

```java
private final Map<String, PaymentService> services;

public PaymentProcessor(
        Map<String, PaymentService> services) {

    this.services = services;
}
```

Conceptually:

```text
bean name → bean instance

"stripe"   → StripePaymentService
"razorpay" → RazorpayPaymentService
"paypal"   → PayPalPaymentService
```

Then:

```java
PaymentService service =
        services.get("stripe");
```

This is useful when selecting an implementation dynamically.

# 25. Bean Scopes

A Spring bean can have different scopes.


# 26. Singleton Scope

Singleton is the **default Spring bean scope**.

Example:

```java
@Service
public class PaymentService {
}
```

By default, Spring maintains:

```text
one PaymentService instance
per ApplicationContext
```

Conceptually:

```text
OrderService ──┐
               │
UserService ───┼──→ PaymentService instance
               │
OtherService ──┘
```

All those services can reference the same bean instance.

---

# 27. Singleton Scope ≠ Thread-Safe

This is an extremely important interview point.

Singleton means:

```text
one instance per ApplicationContext
```

It does **not** mean:

```text
thread-safe
```

Example:

```java
@Service
public class CounterService {

    private int count = 0;

    public void increment() {
        count++;
    }
}
```

If multiple requests/threads access this singleton:

```text
Thread A ──┐
Thread B ──┼──→ same CounterService
Thread C ──┘
```

they can concurrently access:

```java
count
```

and cause race conditions.

### Therefore

Typical Spring singleton services should be:

```text
stateless
```

Prefer:

```java
@Service
public class OrderService {

    public Order calculateOrder(OrderRequest request) {
        // local variables
        // no shared mutable instance state
    }
}
```

### Interview answer

> Singleton scope means one bean instance per ApplicationContext; it does not make the bean thread-safe. That instance can be accessed concurrently by multiple threads, so singleton beans should generally be stateless and avoid shared mutable instance state.

---

# 28. Prototype Scope

Example:

```java
@Scope("prototype")
@Component
public class ReportGenerator {
}
```

Spring creates a new instance whenever the prototype bean is requested from the container.

Conceptually:

```text
getBean()
   ↓
ReportGenerator A

getBean()
   ↓
ReportGenerator B

getBean()
   ↓
ReportGenerator C
```

Compare:

```text
singleton
    ↓
same instance

prototype
    ↓
new instance when requested
```

Important nuance:

Spring manages creation and injection of prototype beans, but it generally does not manage their full destruction lifecycle like it does for singleton beans.

# 29. Request Scope

Mostly relevant in web applications.

Example:

```java

@Component

}
```

There is one bean instance associated with each HTTP request.

Conceptually:

```text
HTTP Request 1 → RequestContext A

HTTP Request 2 → RequestContext B

HTTP Request 3 → RequestContext C
```

# 30. Session Scope

Example:

```java
@SessionScope
@Component

}
```

The bean is associated with an HTTP session.

Conceptually:

```text

User/session B → ShoppingCart B
```

# 32. Circular Dependencies

A circular dependency occurs when beans depend on each other.

Example:

```text
A → B
↑   ↓
└───┘
```

Code:

```java
class A {
    A(B b) {}
}

class B {
    B(A a) {}
}
```

To create `A`:

```text
Need B
```

To create `B`:

```text
Need A
```

But `A` isn't finished.

So:

```text
Create A
   ↓
Need B
   ↓
Create B
   ↓
Need A
   ↓
A isn't available yet
```

---

# 33. Constructor Circular Dependency

Example:

```java
@Service
class A {

    private final B b;

    A(B b) {
        this.b = b;
    }
}
```

```java
@Service
class B {

    private final A a;

    B(A a) {
        this.a = a;
    }
}
```

Spring cannot construct either bean first.

Therefore, constructor circular dependencies fail during bean creation and typically cause application startup to fail.

This is often called **fail-fast behavior**.

---

# 34. Why Constructor Injection Exposes Circular Dependencies

Constructor dependencies must be satisfied **before the object can be created**.

Therefore:

```text
A requires B
B requires A
```

has no valid construction order.

Constructor injection exposes this problem immediately.

This is actually a useful design signal:

> The dependency graph may need to be redesigned.

---

# 35. What About Field/Setter Circular Dependencies?

Spring has mechanisms involving early bean references that can allow some circular dependencies involving setter/field injection to be resolved.

Conceptually:

```text
Create A
   ↓
A exists but isn't fully initialized
   ↓
Create B
   ↓
Inject A into B
   ↓
Inject B into A
```

However:

> A circular dependency being technically resolvable does not mean it is good design.

Circular dependencies usually make code harder to understand, test, and maintain.

A better design might be:

```text
A → C ← B
```

where shared logic is moved into another service.

---

# 36. Complete Example

Suppose we have:

```java
interface PaymentService {

}
```

```java

        implements PaymentService {

    @Override
```



```text
AppConfig
   ↓

PaymentService bean

@Bean orderService(PaymentService)

```

The dependency graph becomes:

```text
PaymentService
```

# 40. `@Component` vs `@Bean`

Remember this simple distinction:

```text
@Component
    ↓
"Spring, discover this class and manage it."

@Bean
    ↓
"Spring, manage the object returned by this method."
```

Use `@Component`/stereotypes when you own the class and want component scanning.

Use `@Bean` when you want explicit control over object creation/configuration, especially for third-party classes.

# 42. How Spring Resolves a Dependency

Suppose:

```java
OrderService(PaymentService paymentService)
```

Spring's simplified mental process is:

```text
Need PaymentService
       ↓
Find matching beans
       ↓
How many candidates?
       │
       ├── 0 → dependency cannot be satisfied
       │
       ├── 1 → inject it
       │
       └── multiple
              ↓
        @Qualifier?
              ↓
        @Primary?
              ↓
        other applicable
        autowiring rules
              ↓
          select bean
```

# 43. Interview Scenarios

## Q1. What exactly does IoC invert?

### Answer

> IoC inverts the responsibility for object creation and dependency wiring. Instead of a class creating and managing its dependencies, the Spring container manages those objects and supplies their dependencies.

---

## Q2. What is Dependency Injection?

### Answer

> Dependency Injection is a mechanism for implementing IoC where dependencies required by a class are supplied by the Spring container rather than being created by the class itself.

---

## Q3. Why is constructor injection preferred over field injection?

### Answer

> Constructor injection makes dependencies explicit, allows required dependencies to be final, improves unit testability because the class can be instantiated directly with mocks, avoids hidden null dependencies, and exposes circular constructor dependencies during bean creation.

---

## Q4. What is the difference between `@Component` and `@Bean`?

### Answer

> `@Component` tells Spring to discover and manage a class through component scanning. `@Bean` explicitly tells Spring to manage the object returned by a method. `@Bean` is particularly useful for third-party classes or when custom construction/configuration is required.

---

## Q5. Is `@Bean` only allowed inside `@Configuration`?

### Answer

> No. `@Bean` methods can also be declared in other Spring-managed components, but `@Configuration` is the standard approach because it provides full configuration-class semantics. Regular components containing `@Bean` methods use lite configuration semantics.

---

## Q6. What is `@Configuration`?

### Answer

> `@Configuration` marks a class as a source of bean definitions. Spring processes its `@Bean` methods and registers the returned objects in the ApplicationContext. It also provides full configuration-class semantics.

---

## Q7. What happens if two beans implement the same interface?

### Answer

> If multiple beans match the required type, Spring needs additional information to resolve the ambiguity. We can use `@Primary` to define a default candidate or `@Qualifier` to explicitly select a specific bean. If we need all implementations, we can inject `List<T>` or `Map<String,T>`.

---

## Q8. Is a Spring singleton bean thread-safe?

### Answer

> No. Singleton scope means one instance per ApplicationContext; it does not make the bean thread-safe. Multiple threads can access the same instance concurrently, so singleton beans should generally be stateless and avoid shared mutable state.

---

## Q9. What is a circular dependency?

### Answer

> A circular dependency occurs when beans depend on each other, such as A depending on B and B depending on A. With constructor injection, Spring cannot satisfy the cycle because neither bean can be constructed first, so bean creation fails and the application typically fails during startup.

---

# 44. 🎤 Say Out Loud — Interview Revision

## IoC

> IoC means Spring takes control of object creation and dependency wiring instead of individual classes creating their own dependencies.

## DI

> Dependency Injection is the mechanism where Spring supplies a class's dependencies instead of the class constructing them itself.

## Constructor Injection

> Constructor injection is preferred because dependencies are explicit, required dependencies can be final, unit testing is easier, and circular dependencies are exposed during bean creation.

## Field Injection

> Field injection hides dependencies, makes unit testing harder, prevents natural use of final fields, and allows an object to exist before its required dependencies are injected.

## Singleton

> Spring singleton means one bean instance per ApplicationContext, not one instance per thread and not necessarily thread-safe. Singleton beans should generally be stateless.

## Two Matching Beans

> If multiple beans match a dependency type, I can use `@Primary` to define the default candidate or `@Qualifier` to explicitly select a particular bean. If I need all implementations, I can inject a `List<T>` or `Map<String,T>`.

## Circular Dependency

> A constructor cycle such as A depending on B and B depending on A cannot be satisfied, so Spring fails bean creation. Some setter or field cycles may be resolvable through early references, but circular dependencies should generally be eliminated through better design.
