# 3.4 Config, Profiles & Actuator

## 1. Externalized Configuration

### What problem are we solving?

Suppose an application connects to a database.

Hard-coding configuration is a bad idea:

```java
String url = "jdbc:mysql://localhost:3306/mydb";
String username = "root";
String password = "password123";
```

The same application may run in:

- Local
- Development
- QA
- Production

Each environment can have different database URLs, credentials, API keys, ports, timeouts, etc.

Spring Boot supports **externalized configuration**, which means configuration can be supplied outside the Java source code.

Conceptually:

```text
Java Application
       |
       v
Reads configuration
       |
       v
External configuration sources
       |
       +--> application.yml
       +--> application-{profile}.yml
       +--> Environment variables
       +--> Command-line arguments
```

The same application artifact can therefore run with different configuration.

---

# 2. `application.yml`

A common configuration file is:

```text
src/main/resources/application.yml
```

Example:

```yaml
server:
  port: 8080

app:
  name: MyApplication
  timeout: 5000
```

Spring Boot automatically loads configuration from supported configuration sources.

---

# 3. `application.properties`

The same configuration can be written using properties:

```properties
server.port=8080

app.name=MyApplication
app.timeout=5000
```

YAML:

```yaml
server:
  port: 8080

app:
  name: MyApplication
  timeout: 5000
```

Both represent configuration; the choice is mainly a matter of format and project convention.

---

# 4. Why Externalized Configuration?

Suppose development uses:

```yaml
database:
  url: jdbc:mysql://localhost:3306/mydb
```

Production may use:

```yaml
database:
  url: jdbc:mysql://production-db:3306/mydb
```

We should not write:

```java
if (production) {
    // production URL
} else {
    // local URL
}
```

Instead, the application reads the configuration from outside the Java code.

The important idea is:

```text
Same application JAR
        |
        +--> Development configuration
        |
        +--> QA configuration
        |
        +--> Production configuration
```

---

# 5. Property Precedence

Spring Boot can receive the same property from multiple sources.

For example:

### `application.yml`

```yaml
server:
  port: 8080
```

### Environment variable

```text
SERVER_PORT=9090
```

### Command-line argument

```bash
java -jar app.jar --server.port=7070
```

The higher-precedence source overrides the lower-precedence source.

For the simplified interview model:

```text
Command-line arguments
        ↓
Environment variables
        ↓
application-{profile}.yml
        ↓
application.yml
```

Therefore the final value in the example is:

```text
7070
```

because the command-line argument has higher precedence.

> **Interview note:** Spring Boot has a more detailed property-source precedence order than this simplified four-level model. If the interviewer asks for the exact complete order, mention that there are additional sources such as system properties, test-specific properties, and configuration imports.

### Interview answer

> Spring Boot supports externalized configuration so the same application can run in different environments without changing code. Multiple property sources can provide the same key, and higher-precedence sources override lower-precedence sources.

---

# 6. `@Value`

`@Value` is a simple way to inject an individual configuration property.

Suppose:

```yaml
app:
  name: MyApplication
```

Java:

```java
@Service
public class MyService {

    @Value("${app.name}")
    private String appName;

    public void printName() {
        System.out.println(appName);
    }
}
```

The value of:

```text
app.name
```

is injected into:

```java
appName
```

---

## Default Value with `@Value`

You can specify a default:

```java
@Value("${app.timeout:5000}")
private int timeout;
```

Meaning:

```text
If app.timeout exists
        |
        +--> use its value

Otherwise
        |
        +--> use 5000
```

---

# 7. Problem with Too Many `@Value` Fields

Suppose configuration contains:

```yaml
app:
  name: MyApplication
  timeout: 5000
  max-users: 1000
  retry-count: 3
  enabled: true
```

Using `@Value` repeatedly:

```java
@Value("${app.name}")
private String name;

@Value("${app.timeout}")
private int timeout;

@Value("${app.max-users}")
private int maxUsers;

@Value("${app.retry-count}")
private int retryCount;

@Value("${app.enabled}")
private boolean enabled;
```

This works, but becomes difficult to maintain as the configuration grows.

This is where `@ConfigurationProperties` becomes useful.

---

# 8. `@ConfigurationProperties`

`@ConfigurationProperties` binds a group of related configuration properties into a Java object.

Configuration:

```yaml
app:
  name: MyApplication
  timeout: 5000
  max-users: 1000
  retry-count: 3
  enabled: true
```

Java:

```java
@ConfigurationProperties(prefix = "app")
public class AppProperties {

    private String name;
    private int timeout;
    private int maxUsers;
    private int retryCount;
    private boolean enabled;

    // getters and setters
}
```

Spring maps:

```text
app.name
    ↓
name

app.timeout
    ↓
timeout

app.max-users
    ↓
maxUsers

app.retry-count
    ↓
retryCount

app.enabled
    ↓
enabled
```

Spring Boot's relaxed binding supports common naming variations, such as `max-users` binding to `maxUsers`.

---

# 9. Enabling `@ConfigurationProperties`

One common approach is to enable scanning:

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class Application {
}
```

Then:

```java
@ConfigurationProperties(prefix = "app")
public class AppProperties {

    private String name;
    private int timeout;

    // getters/setters
}
```

Another approach is explicit registration:

```java
@EnableConfigurationProperties(AppProperties.class)
```

The exact approach depends on the project setup.

---

# 10. Why `@ConfigurationProperties`?

It is especially useful when you have a configuration group:

```text
app.name
app.timeout
app.max-users
app.retry-count
app.enabled
```

Instead of scattering properties throughout the code:

```text
@ConfigurationProperties
        |
        v
   AppProperties
        |
        +--> name
        +--> timeout
        +--> maxUsers
        +--> retryCount
        +--> enabled
```

This gives you a central, type-safe configuration object.

---

# 11. Configuration Validation

`@ConfigurationProperties` works well with Bean Validation.

Example:

```java
@ConfigurationProperties(prefix = "app")
@Validated
public class AppProperties {

    @NotBlank
    private String name;

    @Min(100)
    private int timeout;

    // getters/setters
}
```

If invalid configuration is supplied, the application can fail during startup.

This is useful because configuration errors are detected early rather than causing unexpected behavior later.

---

# 12. `@Value` vs `@ConfigurationProperties`

| Feature | `@Value` | `@ConfigurationProperties` |
|---|---|---|
| Individual properties | Excellent | Possible |
| Group of properties | Not ideal | Excellent |
| Type-safe configuration object | Limited | Yes |
| Validation | More manual | Excellent with Bean Validation |
| Complex configuration | Awkward | Better |
| Maintainability for large config | Lower | Higher |

### Interview answer

> I use `@Value` for simple individual configuration values. For a group of related application settings, I prefer `@ConfigurationProperties` because it provides type-safe binding, cleaner organization, and validation support.

---

# 13. Spring Profiles

Suppose an application has:

```text
Development
QA
Production
```

Different environments may require different:

- Database URLs
- Logging levels
- API endpoints
- Feature flags
- External service configuration
- Bean implementations

Spring Profiles allow us to activate environment-specific configuration and beans.

---

# 14. `application-{profile}.yml`

Typical files:

```text
application.yml
application-dev.yml
application-test.yml
application-prod.yml
```

### `application.yml`

Common configuration:

```yaml
app:
  name: MyApplication
```

### `application-dev.yml`

```yaml
server:
  port: 8080

logging:
  level:
    root: DEBUG
```

### `application-prod.yml`

```yaml
server:
  port: 80

logging:
  level:
    root: INFO
```

The profile-specific configuration can override common values.

---

# 15. Activating a Profile

You can activate a profile using:

```yaml
spring:
  profiles:
    active: dev
```

Or with a command-line argument:

```bash
java -jar app.jar --spring.profiles.active=prod
```

Or with an environment variable:

```text
SPRING_PROFILES_ACTIVE=prod
```

In deployment environments, environment variables or deployment configuration are commonly preferable to hard-coding the active environment in the application.

---

# 16. Profile Configuration Flow

Suppose:

```text
spring.profiles.active=prod
```

Spring Boot loads the common configuration and applies the production-specific configuration.

Conceptually:

```text
application.yml
       +
application-prod.yml
       |
       v
Final Environment Configuration
```

If both define:

```yaml
server:
  port: ...
```

the profile-specific value can override the common value.

---

# 17. `@Profile`

Profiles can also control bean registration.

Example:

```java
@Service
@Profile("dev")
public class DevEmailService implements EmailService {

    @Override
    public void send(String email) {
        System.out.println("Fake email: " + email);
    }
}
```

Production:

```java
@Service
@Profile("prod")
public class ProductionEmailService implements EmailService {

    @Override
    public void send(String email) {
        // Send actual email
    }
}
```

If:

```text
spring.profiles.active=dev
```

Spring registers the development implementation.

If:

```text
spring.profiles.active=prod
```

Spring registers the production implementation.

Conceptually:

```text
              Active Profile
                   |
        +----------+----------+
        |                     |
       dev                   prod
        |                     |
        v                     v
DevEmailService      ProductionEmailService
```

---

# 18. Real-World Profile Example

During development, we may not want to send real emails.

```java
@Service
@Profile("dev")
public class FakeEmailService implements EmailService {

    public void send(String email) {
        System.out.println("Fake email: " + email);
    }
}
```

Production:

```java
@Service
@Profile("prod")
public class RealEmailService implements EmailService {

    public void send(String email) {
        // Real email provider
    }
}
```

This allows the same application to use different implementations depending on the active profile.

---

# 19. `application.yml` vs `application-{profile}.yml`

Think of:

```text
application.yml
```

as the common/default configuration.

And:

```text
application-dev.yml
application-test.yml
application-prod.yml
```

as environment-specific configuration.

Example:

### application.yml

```yaml
app:
  name: MyApp
  timeout: 5000
```

### application-prod.yml

```yaml
app:
  timeout: 10000
```

With `prod` active, conceptually:

```text
name = MyApp
timeout = 10000
```

# 20. Spring Boot Actuator

Spring Boot Actuator provides **production-oriented monitoring and management capabilities**.

It exposes endpoints that provide information about the running application.

Examples:

```text
/actuator/health
/actuator/info
/actuator/metrics
```

These endpoints can help answer questions such as:

```text
Is the application healthy?
What metrics are available?
How much memory is being used?
How many HTTP requests are occurring?
```

---

# 21. Adding Actuator

With Maven:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

After adding the dependency, Actuator endpoints can be configured and exposed.

---

# 22. `/actuator/health`

One of the most important endpoints is:

```text
GET /actuator/health
```

Example:

```json
{
  "status": "UP"
}
```

It reports the application's health status based on available health indicators.

It can be used by infrastructure such as:

```text
Load Balancer
      |
      v
Health Check
      |
      v
/actuator/health
      |
      v
Spring Boot Application
```

---

# 23. Health Checks and Dependencies

Health information can include health indicators for dependencies such as databases, depending on the application's configuration and available integrations.

For example, a database problem can cause the application's relevant health indicator to report a problem.

This is useful for monitoring and orchestration.

---

# 24. `/actuator/info`

The info endpoint can expose application information.

Example configuration:

```yaml
info:
  app:
    name: MyApplication
    version: 1.0.0
```

Then:

```text
/actuator/info
```

can expose configured application information.

Do not expose secrets or sensitive internal information through this endpoint.

---

# 25. `/actuator/metrics`

The metrics endpoint exposes application metrics.

For example:

```text
/actuator/metrics
```

can show available metric names.

An individual metric can then be queried, such as:

```text
/actuator/metrics/jvm.memory.used
```

Metrics can help answer:

```text
How much memory is being used?
How many requests are occurring?
How long are requests taking?
How many errors are occurring?
```

The exact metrics available depend on the application, Spring Boot version, dependencies, and configuration.

---

# 26. Actuator Endpoint Exposure

Not every endpoint should automatically be exposed publicly.

For example:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
```

This exposes selected endpoints over HTTP.

Production applications should carefully control actuator exposure and protect sensitive endpoints using appropriate security and network controls.

---

# 27. Logging

Logging is another important part of application configuration.

Instead of:

```java
System.out.println("Processing order");
```

use a logging framework:

```java
private static final Logger log =
        LoggerFactory.getLogger(MyService.class);
```

Then:

```java
log.info("Processing order {}", orderId);
log.warn("Order processing is slow");
log.error("Failed to process order", exception);
```

---

# 28. SLF4J and Logback

A common Spring Boot logging setup is:

```text
Application code
       |
       v
     SLF4J
       |
       v
   Logback
```

### SLF4J

SLF4J provides a logging abstraction/API.

Your application code generally uses:

```java
Logger
```

without being tightly coupled to a particular logging implementation.

### Logback

Logback is a common logging implementation used by Spring Boot.

This separation makes logging configuration more flexible.

---

# 29. Logging Levels

Common logging levels:

```text
TRACE
DEBUG
INFO
WARN
ERROR
```

Conceptually:

```text
TRACE
  ↓
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
```

If the configured level is:

```yaml
logging:
  level:
    root: INFO
```

then INFO, WARN, and ERROR messages are logged, while DEBUG and TRACE messages are normally filtered out.

---

# 30. Package-Specific Logging

You don't always need DEBUG logging for the entire application.

Example:

```yaml
logging:
  level:
    root: INFO
    com.example.myapp: DEBUG
```

Meaning:

```text
Entire application
       |
       +--> INFO

com.example.myapp
       |
       +--> DEBUG
```

This is useful when debugging a particular part of the application without generating excessive logs everywhere.

---

# 31. Logging to a File

You can configure file logging:

```yaml
logging:
  file:
    name: logs/application.log
```

Then logs can be written to:

```text
logs/application.log
```

In production, applications often send logs to centralized logging systems rather than depending only on local files.

---

# 32. Logging Configuration File

For more advanced Logback configuration, you may use a file such as:

```text
logback-spring.xml
```

This can be useful when you need more detailed logging configuration than simple `application.yml` properties provide.

For example, you can configure:

- Log patterns
- Console appenders
- File appenders
- Rolling files
- Package-specific levels
- Profile-specific logging behavior

---

# 33. Interview Scenario: Multiple Environments

### Interviewer

> You have the same Spring Boot application running in development, QA, and production. Database URLs and logging levels are different. How would you handle it?

### Answer

> I would externalize environment-specific configuration instead of hard-coding it. I would keep common settings in `application.yml` and environment-specific overrides in files such as `application-dev.yml` and `application-prod.yml`. I would activate the appropriate profile using `spring.profiles.active`, an environment variable, or a command-line argument. For grouped application configuration, I would generally use `@ConfigurationProperties`.

---

# 34. Interview Scenario: `@Value` vs `@ConfigurationProperties`

### Interviewer

> What's the difference between `@Value` and `@ConfigurationProperties`?

### Answer

> `@Value` is convenient for injecting individual properties, while `@ConfigurationProperties` is better for binding a group of related configuration properties into a type-safe object. `@ConfigurationProperties` also works well with validation and makes larger configuration structures easier to maintain.

---

# 35. Interview Scenario: Spring Profile

### Interviewer

> What is a Spring Profile?

### Answer

> A Spring Profile allows us to conditionally activate configuration and beans for different environments. For example, we can have `application-dev.yml` and `application-prod.yml`, and use `@Profile("dev")` or `@Profile("prod")` to create environment-specific beans.

---

# 36. Interview Scenario: Actuator

### Interviewer

> What is Spring Boot Actuator?

### Answer

> Spring Boot Actuator provides production-oriented monitoring and management endpoints for a Spring Boot application. Common endpoints include health, info, and metrics. For example, `/actuator/health` can be used by infrastructure to determine the application's health.

---

# 37. Interview Scenario: Why Externalize Configuration?

### Interviewer

> Why shouldn't we hard-code database URLs or API keys in Java code?

### Answer

> Because configuration changes between environments and may contain sensitive values. Externalized configuration allows the same application artifact to run in different environments without changing the code. Secrets should also be managed using appropriate secret-management mechanisms rather than committed to source control.

---

# 38. Important Interview Distinction

Do not confuse:

```text
Profile
```

with:

```text
Property source
```

A **profile** determines which environment-specific configuration and beans are active.

A **property source** is a source from which configuration values are obtained.

For example:

```text
Profile:
    prod

Property files:
    application.yml
    application-prod.yml

Environment variable:
    SPRING_DATASOURCE_URL

Command-line:
    --server.port=8080
```

These concepts work together but are not the same thing.

# 40. Quick Revision

## Externalized Configuration

> Keep environment-specific configuration outside application code so the same application can run in different environments.

## Property Precedence

> Higher-precedence property sources override lower-precedence sources. Command-line arguments and environment variables can override configuration-file values.

## `@Value`

> Best suited for simple individual property injection.

Example:

```java
@Value("${app.name}")
private String appName;
```

## `@ConfigurationProperties`

> Best suited for type-safe binding of a group of related configuration properties.

Example:

```java
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private String name;
    private int timeout;
}
```

## Profiles

> Profiles allow environment-specific configuration and conditional bean registration.

Example:

```text
application-dev.yml
application-prod.yml
```

and:

```java
@Profile("prod")
```

## Actuator

> Provides production-oriented monitoring and management endpoints such as health, info, and metrics.

## Logging

> Use SLF4J-based logging with appropriate log levels instead of `System.out.println()`.
