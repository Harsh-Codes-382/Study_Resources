# 1. What is a Spring Bean?

A **Spring Bean** is an object whose creation, configuration, dependency injection, and lifecycle are managed by the Spring IoC container.

Without Spring:

```java
UserService service = new UserService();
```

With Spring:

```java
@Service
public class UserService {
}
```

Spring discovers the class and creates/manages the object.

Conceptually:

```text
Spring Container
      |
      | creates
      v
UserService object
      |
      | manages
      v
Spring Bean
```

### Interview definition

> A Spring Bean is an object that is instantiated, configured, and managed by the Spring IoC container.

---

# 2. Spring Bean Lifecycle

A simplified Spring Bean lifecycle is:

```text
Application starts
       |
       v
Instantiate bean
       |
       v
Populate properties / inject dependencies
       |
       v
Initialization callbacks
       |
       +--> @PostConstruct
       |
       +--> InitializingBean.afterPropertiesSet()
       |
       v
Bean is ready for use
       |
       v
Application runs
       |
       v
Application shuts down
       |
       v
Destruction callbacks
       |
       +--> @PreDestroy
       |
       v
Bean destroyed
```

The simplified sequence to remember:

```text
instantiate
    ↓
dependency injection
    ↓
initialization
    ↓
use
    ↓
destruction
```

# 3. Step 1 — Instantiation

Spring first creates the bean object.

Example:

```java
@Service
public class UserService {

}
```

Conceptually, Spring needs to create something similar to:

```java
UserService service = new UserService();
```

This step is called **instantiation**.

### Interview definition

> Instantiation is the stage where the Spring container creates the bean object.

---

# 4. Step 2 — Populate Properties / Dependency Injection

After creating the bean, Spring injects its dependencies.

Example:

```java
@Repository
public class UserRepository {

}
```

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

Conceptually:

```java
UserRepository repository = new UserRepository();

UserService service =
        new UserService(repository);
```

The actual Spring container performs this dependency management for you.

The flow is:

```text
Create UserRepository
        |
        v
Create UserService
        |
        v
Inject UserRepository
```

This is the dependency injection/population phase.

---

# 5. Step 3 — Initialization

After dependencies have been injected, Spring performs initialization callbacks.

Two commonly discussed mechanisms are:

```java
@PostConstruct
```

and:

```java
InitializingBean
```

---

# 6. `@PostConstruct`

`@PostConstruct` marks a method that should run after dependency injection has completed.

Example:

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }

    @PostConstruct
    public void init() {
        System.out.println("UserService initialized");
    }
}
```

Conceptually:

```text
Constructor
    ↓
Dependencies injected
    ↓
@PostConstruct
```

Therefore, initialization logic in `@PostConstruct` can use the injected dependencies.

### Typical use cases

```java
@PostConstruct
public void init() {
    loadConfiguration();
    initializeCache();
}
```

Examples:

- Initialize an in-memory cache
- Validate configuration
- Prepare resources
- Perform startup initialization

### Interview definition

> `@PostConstruct` is used for initialization logic that should execute after dependency injection has completed.

---

# 7. `InitializingBean`

Spring also provides the `InitializingBean` interface.

Example:

```java
@Service
public class UserService implements InitializingBean {

    @Override
    public void afterPropertiesSet() {
        System.out.println("Bean initialized");
    }
}
```

Spring calls:

```java
afterPropertiesSet();
```

after the bean's properties have been populated.

Conceptually:

```text
Create bean
    ↓
Inject dependencies
    ↓
afterPropertiesSet()
    ↓
Bean ready
```

### `@PostConstruct` vs `InitializingBean`

For normal application code, `@PostConstruct` is often preferred because it avoids directly coupling the class to Spring's lifecycle interface.

Example:

```java
@PostConstruct
public void init() {
    // initialization
}
```

versus:

```java
public class UserService implements InitializingBean {

    @Override
    public void afterPropertiesSet() {
        // initialization
    }
}
```

---

# 8. Step 4 — Bean Is Ready for Use

After initialization completes, the bean is available for other beans and application code to use.

Example:

```java
@RestController
public class UserController {

    private final UserService service;

    public UserController(UserService service) {
        this.service = service;
    }
}
```

The controller receives the Spring-managed `UserService`.

Conceptually:

```text
Instantiate
     ↓
Inject dependencies
     ↓
@PostConstruct
     ↓
Bean ready
     ↓
Other beans use it
```

# 9. Step 5 — Destruction

When the Spring application context shuts down, Spring can invoke destruction callbacks for beans whose lifecycle it manages.

One common mechanism is:

```java
@PreDestroy
```

Example:

```java
@Service
public class UserService {

    @PreDestroy
    public void cleanup() {
        System.out.println("Cleaning up...");
    }
}
```

Conceptually:

```text
Application running
       |
       v
     Bean
       |
       v
Application shutting down
       |
       v
 @PreDestroy
       |
       v
Bean destroyed
```

### Typical use cases

```java
@PreDestroy
public void cleanup() {
    closeConnection();
    releaseResource();
}
```

Examples:

- Release resources
- Close custom connections
- Stop custom background work
- Clear resources owned by the bean

### Interview definition

> `@PreDestroy` is used for cleanup logic that Spring invokes before a managed bean is destroyed.

# 10. Complete Bean Lifecycle Example

```java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        System.out.println("1. Constructor");
        this.repository = repository;

    @PostConstruct

    @PreDestroy
    public void cleanup() {
        System.out.println("3. PreDestroy");

```

```text

       |
       v
Dependency Injection
       |
       v
@PostConstruct
       |
       v
Bean available
       |
       v
Application runs
       |
       v
Application shuts down
       |
       v
@PreDestroy
       |
       v
Bean destroyed
```

# 11. Singleton vs Prototype and Destruction

By default, Spring beans have singleton scope.

```java
@Scope("singleton")
```

This means:

```text
One bean instance per Spring ApplicationContext
```

For singleton beans, Spring manages their lifecycle and destruction callbacks.

Prototype scope:

```java
@Scope("prototype")
```

means Spring creates a new instance each time the bean is requested.

An important interview point:

> Spring generally does not manage the complete destruction lifecycle of prototype instances after handing them to the caller.

Therefore, destruction callbacks such as `@PreDestroy` should not be assumed to be automatically invoked for prototype beans.

A typical Spring Boot application starts with:

```text
@SpringBootApplication
        |
        +---- @Configuration
        |
        +---- @EnableAutoConfiguration
        |
        +---- @ComponentScan
```

# 13. `@Configuration`

`@Configuration` tells Spring that a class contains bean configuration.

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}
```

Spring sees the `@Bean` method and registers the returned object as a Spring Bean.

Conceptually:

```text
@Configuration
       |
       v
Bean definitions
       |
       v
@Bean methods
       |
       v
Spring-managed objects
```

### Important connection with `@Bean`

There are two common ways to register beans.

### Component scanning

```java
@Service
public class UserService {
}
```

Spring discovers it through component scanning.

### Explicit bean registration

```java
@Configuration
public class AppConfig {

    @Bean
    public UserService userService() {
        return new UserService();
    }
}
```

Here you explicitly tell Spring to register the returned object.

---

# 14. `@ComponentScan`

`@ComponentScan` tells Spring where to look for component classes.

For example:

```java
@Component
@Service
@Repository
@Controller
```

Suppose the project structure is:

```text
com.example
   |
   +-- Application.java
   |
   +-- service
   |      UserService.java
   |
   +-- repository
          UserRepository.java
```

If the application class is:

```java
package com.example;

@SpringBootApplication
public class Application {
}
```

component scanning commonly starts from the package containing the application class and scans its subpackages.

It can find:

```java
@Service
public class UserService {
}
```

and:

```java
@Repository
public class UserRepository {
}
```

and register them as beans.

### Interview definition

> `@ComponentScan` tells Spring which packages to scan for component classes such as `@Component`, `@Service`, `@Repository`, and `@Controller`.

# 15. `@EnableAutoConfiguration`

This is one of the most important Spring Boot features.

It tells Spring Boot to automatically configure appropriate application infrastructure based on the application's environment.

For example, depending on the dependencies and configuration, Boot can configure things related to:

- Web/MVC applications
- JSON handling
- Embedded web servers
- Database connectivity
- JPA/Hibernate
- Transactions
- Other framework integrations

Instead of configuring every infrastructure component manually, Boot provides sensible defaults.

Conceptually:

```text
Dependencies
     +
Application properties
     +
Existing beans
     +
Conditions
     |
     v
AutoConfiguration
     |
     v
Configured Spring Beans
```

# 16. What Is Auto-Configuration?

Spring Boot auto-configuration means:

> Spring Boot automatically configures common infrastructure when the required conditions are satisfied.

Imagine a database application.

Without Boot, you might need to manually configure:

```text
DataSource
Connection pool
Transaction manager
JPA
EntityManager
Hibernate
```

With Spring Boot, much of this configuration can be automatically provided when the required dependencies and properties are present.

Conceptually:

```text
Add dependency
      +
Configure properties
      |
      v
Spring Boot detects environment
      |
      v
Conditional auto-configuration
      |
      v
Infrastructure beans
```

# 17. Conditional Auto-Configuration

Spring Boot does not blindly configure everything.

It uses conditions to determine whether a configuration should be applied.

Common conditional annotations include:

```java
@ConditionalOnClass
@ConditionalOnMissingBean
@ConditionalOnBean
@ConditionalOnProperty
@ConditionalOnMissingClass
```

The basic idea is:

> Only apply this configuration when its conditions are satisfied.

---

# 18. `@ConditionalOnClass`

Example:

```java
@ConditionalOnClass(DataSource.class)
```

This means the configuration is applicable when `DataSource` is available on the classpath.

Conceptually:

```text
Is DataSource available?
        |
    +---+---+
    |       |
   YES      NO
    |        |
    v        v
Configure   Skip this
feature     configuration
```

This is one way Spring Boot determines what libraries/features are available.

---

# 19. `@ConditionalOnMissingBean`

This condition is extremely important.

Suppose Boot wants to provide a default `DataSource`.

It can use:

```java
@ConditionalOnMissingBean(DataSource.class)
```

Meaning:

> Create the default configuration only if the application hasn't already provided a `DataSource`.

Suppose you define:

```java
@Bean
public DataSource dataSource() {
    return myCustomDataSource();
}
```

Then:

```text
Application already has DataSource
          |
          v
@ConditionalOnMissingBean fails
          |
          v
Boot backs off
          |
          v
Your custom DataSource is used
```

This is why Spring Boot auto-configuration is customizable.

### Important interview phrase

> **Auto-configuration provides sensible defaults and backs off when the application provides its own configuration.**

---

# 20. `@ConditionalOnProperty`

Boot can also condition configuration on an application property.

Example:

```java
@ConditionalOnProperty(
    name = "feature.payment",
    havingValue = "true"
)
```

Then:

```properties
feature.payment=true
```

means the condition is satisfied.

Conceptually:

```text
feature.payment=true
        |
        v
Condition satisfied
        |
        v
Configuration can be applied
```

If the property does not satisfy the condition, that configuration is not applied.

---

# 21. Other Useful Conditions

### `@ConditionalOnBean`

Apply configuration when a particular bean already exists.

```java
@ConditionalOnBean(DataSource.class)
```

Meaning:

> Apply this configuration if a `DataSource` bean exists.

---

### `@ConditionalOnMissingClass`

Apply configuration when a particular class is NOT available.

Conceptually:

```text
Required class absent
       |
       v
Condition satisfied
       |
       v
Configuration can apply
```

# 22. How Auto-Configuration Decides What to Wire

This is one of your important interview "say out loud" topics.

### Strong interview answer

> "Spring Boot auto-configuration looks at the application's classpath, configuration properties, existing beans, and conditional rules to decide what configuration should be applied. For example, `@ConditionalOnClass` checks whether a required class is available, `@ConditionalOnProperty` checks application properties, and `@ConditionalOnMissingBean` allows Boot to provide a default only when the application hasn't already defined that bean."

### Short version

Remember:

```text
Classpath
   +
Conditions
   +
Properties
   +
Existing Beans
   =
Auto-Configuration Decision
```

# 24. Why Do Starters Exist?

Without starters, developers would need to manually identify and manage many related dependencies.

A starter provides a convenient group of dependencies for a particular use case.

Conceptually:

```text
Want web application?
        |
        v
spring-boot-starter-web
        |
        v
Relevant dependencies
        |
        v

        |
        v

        |
```

### Easy memory trick

> **Starter = dependencies**

> **Auto-configuration = configuration**

They work together, but they are not the same thing.

This is an important distinction.

### Starter

A starter mainly helps bring the relevant dependencies onto the classpath.

```text
Starter
   |
   v
Dependencies
   |
   v

```

### Auto-Configuration

Auto-configuration looks at those dependencies and other conditions and configures appropriate infrastructure.

```text

     +

     +

     |
     v

     |
```

Therefore:


# 26. Stereotype Annotations

Common Spring stereotype annotations include:

```java
@Component
@Service
@Repository
@Controller
```

They communicate that a class is a Spring-managed component and indicate its intended role.

---

# 27. `@Component`

`@Component` is the generic stereotype.

Example:

```java
@Component
public class EmailValidator {

    public boolean isValid(String email) {
        return email != null && email.contains("@");
    }
}
```

During component scanning, Spring can discover this class and register it as a bean.

Use `@Component` when the class is a Spring-managed component but does not have a more specific layer-oriented role.

### Remember

```text
@Component
    |
    v
Generic Spring component
```

---

# 28. `@Service`

`@Service` is intended for the service/business-logic layer.

Example:

```java
@Service
public class OrderService {

    public void placeOrder() {
        // Business logic
    }
}
```

It communicates:

> This class represents application/service-layer logic.

Conceptually:

```text
@Service
   |
   v
@Component semantics
   |
   v
Spring Bean
```

The main distinction is the semantic intent of the annotation.

---

# 29. `@Repository`

`@Repository` is intended for the persistence/data-access layer.

Example:

```java
@Repository
public class UserRepository {

    public User findById(Long id) {
        // Database access
        return null;
    }
}
```

It communicates:

> This class is responsible for data access/persistence.

But `@Repository` has an important additional behavior:

> It participates in Spring's exception translation mechanism.

---

# 30. What Does `@Repository` Add?

This is a very common interview question.

Different persistence technologies can throw different exception types.

For example:

```text
JDBC-specific exception
Hibernate-specific exception
JPA-related persistence exception
```

Spring can translate persistence-related exceptions into Spring's data-access exception hierarchy.

Conceptually:

```text
Database / persistence operation
          |
          v
Technology-specific exception
          |
          v
Spring exception translation
          |
          v
DataAccessException hierarchy
```

This prevents upper application layers from being tightly coupled to persistence-specific exception types.

### Strong interview answer

> "`@Repository` marks a class as a persistence or data-access component and participates in Spring's exception translation mechanism, which translates persistence-specific exceptions into Spring's `DataAccessException` hierarchy."

---

# 31. `@Controller`

`@Controller` identifies a class as part of the web/presentation layer.

Example:

```java
@Controller
public class UserController {

    @GetMapping("/users")
    public String users() {
        return "users";
    }
}
```

It is commonly used in Spring MVC applications where controller methods can return view names.

For REST APIs, you will commonly see:

```java
@RestController
public class UserController {
}
```

`@RestController` is effectively:

```text
@Controller
+
@ResponseBody
```

This makes it convenient for REST endpoints that return response data directly.

# 33. Are `@Component`, `@Service`, `@Repository`, and `@Controller` Different?

At the basic component-scanning level, they are all stereotypes used to identify Spring-managed components.

Conceptually:

```text
@Component
   |
   +---- @Service
   |
   +---- @Repository
   |
   +---- @Controller
```

The important distinction is **intent and additional semantics**.

| Annotation | Intended role | Important point |
|---|---|---|
| `@Component` | Generic component | General-purpose stereotype |
| `@Service` | Business/service layer | Communicates business logic role |
| `@Repository` | Data-access layer | Exception translation |
| `@Controller` | Web/presentation layer | Spring MVC controller |
| `@RestController` | REST API layer | `@Controller` + `@ResponseBody` |

Do not say:

> "`@Service` creates a bean but `@Component` doesn't."

That is incorrect.

Both can result in Spring-managed beans when component scanning applies.

# 35. Auto-Configuration "Back Off" Example

Suppose Spring Boot can automatically create a `DataSource`.

You define your own:

```java
@Bean

    return myCustomDataSource();
}
```

Boot can have a condition such as:

```java
@ConditionalOnMissingBean(DataSource.class)
```

The logic becomes:

```text
Does application already have DataSource?
              |
        +-----+-----+
        |           |
       YES          NO
        |            |
        v            v
Boot backs off   Create default
                 DataSource
```

This is why Boot's defaults are generally customizable.

### Interview phrase

> "Spring Boot auto-configuration backs off when the application provides its own configuration."

# 37. Important Interview Questions

## Q1. What is the Spring Bean lifecycle?

### Answer

> A Spring bean is instantiated by the container, its dependencies and properties are populated, initialization callbacks such as `@PostConstruct` or `InitializingBean.afterPropertiesSet()` are invoked, and then the bean is available for use. During application shutdown, destruction callbacks such as `@PreDestroy` can be invoked before the bean is destroyed.

---

## Q2. What is `@SpringBootApplication`?

### Answer

> `@SpringBootApplication` is a convenience annotation that combines `@Configuration`, `@EnableAutoConfiguration`, and `@ComponentScan`.

---

## Q3. What does `@Configuration` do?

### Answer

> `@Configuration` marks a class as a source of Spring bean definitions, commonly using `@Bean` methods.

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public UserService userService() {
        return new UserService();
    }
}
```

---

## Q4. What does `@ComponentScan` do?

### Answer

> `@ComponentScan` tells Spring which packages to scan for component classes such as `@Component`, `@Service`, `@Repository`, and `@Controller`.

---

## Q5. What is Spring Boot auto-configuration?

### Answer

> Auto-configuration automatically configures common application infrastructure based on the dependencies available on the classpath, configuration properties, existing beans, and conditional rules.

---

## Q6. How does auto-configuration decide what to wire?

### Answer

> "It mainly uses the classpath, conditions, properties, and existing beans."

More detailed:

> "For example, `@ConditionalOnClass` checks whether a class is available, `@ConditionalOnProperty` checks configuration properties, and `@ConditionalOnMissingBean` allows Boot to provide a default only when the application hasn't already defined that bean."

---

## Q7. What is a Spring Boot starter?

### Answer

> A starter is a convenient dependency bundle for a particular capability such as web development, JPA, or testing. It brings relevant dependencies onto the classpath, after which Spring Boot auto-configuration can configure the appropriate infrastructure.

---

## Q8. Difference between starter and auto-configuration?

### Answer

> A starter primarily provides the relevant dependencies, while auto-configuration uses those dependencies together with conditions, properties, and existing beans to configure the application.

Remember:

```text
Starter = dependencies
AutoConfiguration = configuration
```

---

## Q9. Difference between `@Component`, `@Service`, and `@Repository`?

### Answer

> `@Component` is the generic stereotype. `@Service` indicates the business/service layer. `@Repository` indicates the persistence/data-access layer and participates in exception translation.

---

## Q10. What does `@Repository` add?

### Strong answer

> "`@Repository` marks a class as a data-access component and participates in Spring's exception translation mechanism, which translates persistence-specific exceptions into Spring's `DataAccessException` hierarchy."

---

## Q11. Why doesn't Spring Boot auto-configure everything?

### Answer

> Spring Boot uses conditions so that configuration is applied only when appropriate. This avoids unnecessary configuration and allows applications to customize or replace Boot's defaults.

---

# 41. One-Minute Interview Answer

If an interviewer asks you to explain this entire topic, you can say:

> "A Spring Bean is an object managed by the Spring IoC container. Its simplified lifecycle is instantiation, dependency injection, initialization using callbacks such as `@PostConstruct` or `InitializingBean`, normal use, and destruction using callbacks such as `@PreDestroy`.
>
> In Spring Boot, `@SpringBootApplication` combines `@Configuration`, `@EnableAutoConfiguration`, and `@ComponentScan`. Component scanning finds classes annotated with stereotypes such as `@Component`, `@Service`, `@Repository`, and `@Controller`.
>
> Auto-configuration provides sensible defaults based on the application's classpath, properties, existing beans, and conditional annotations. For example, `@ConditionalOnClass` checks the classpath, `@ConditionalOnProperty` checks properties, and `@ConditionalOnMissingBean` allows Boot to back off when the application already provides a bean.
>
> Starters are dependency bundles that make it convenient to add capabilities such as web development or JPA. Finally, `@Repository` represents the data-access layer and also participates in Spring's exception translation mechanism, converting persistence-specific exceptions into Spring's `DataAccessException` hierarchy."
