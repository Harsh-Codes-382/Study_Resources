# Spring Security + JWT — Interview & Real-Application Notes

> Goal: Understand Spring Security as a system, not as a collection of annotations. These notes cover the complete login flow, JWT request flow, filter chain, authentication/authorization, providers, customization points, endpoint security, statelessness, password verification, refresh tokens, CORS/CSRF, and interview answers.

---

## 1. The Big Picture

There are **two major flows** to keep separate:

### Login flow

The user has **credentials** and wants to authenticate.

```text
POST /auth/login
        |
        | email + password
        v
Spring Security Filter Chain
        |
        v
DispatcherServlet
        |
        v
AuthController
        |
        v
AuthenticationManager
        |
        v
ProviderManager
        |
        v
DaoAuthenticationProvider
        |
        +------------------------+
        |                        |
        v                        v
UserDetailsService        PasswordEncoder
        |                        |
        v                        v
UserRepository              BCrypt
        |                        |
        v                        |
     Database                    |
        |                        |
        +------> UserDetails <---+
                    |
                    v
          Password matches?
             /          \
           NO            YES
           |              |
           v              v
       Authentication   Authentication
         Exception       SUCCESS
                            |
                            v
                       JwtService
                            |
                            v
                       Signed JWT
                            |
                            v
                       HTTP Response
```

### Subsequent authenticated request

The client already has a JWT.

```text
GET /orders
Authorization: Bearer <JWT>
        |
        v
Spring Security Filter Chain
        |
        v
JWT/Bearer authentication
        |
        v
Validate JWT
  - signature
  - expiration
  - issuer/audience if configured
        |
        v
Create Authentication
        |
        v
SecurityContext
        |
        v
AuthorizationFilter
        |
        +-------------------+
        |                   |
    authorized          unauthorized
        |                   |
        v                   v
   Controller              403
```

**Core distinction:**

```text
LOGIN:
credentials -> AuthenticationManager -> Authentication -> JWT

NORMAL REQUEST:
JWT -> Authentication -> SecurityContext -> Authorization
```

Do not mentally combine these into one identical pipeline.

# 2. Authentication vs Authorization

## Authentication

> **Who are you?**

Example:

```text
email + password
       |
       v
Are these credentials valid?
```

If yes, the request/user is authenticated.

## Authorization

> **What are you allowed to do?**

Example:

```text
Authenticated user = ROLE_USER

GET /admin/users
requires ROLE_ADMIN
```

Authentication can succeed while authorization fails.

### HTTP status convention

```text
401 Unauthorized
    -> Authentication is missing/invalid.

403 Forbidden
    -> Authentication succeeded, but access is not permitted.
```

# 4. SecurityFilterChain

The security filter chain is the HTTP interception pipeline.

Conceptually:

```text
HTTP Request
     |
     v
Security Filter Chain
     |
     +--> SecurityContext handling
     +--> Authentication mechanisms
     +--> Exception handling
     +--> Authorization
     |
     v
DispatcherServlet
     |
     v
Controller
```

This is similar in concept to Node/Express middleware:

```javascript
app.use(authMiddleware);
app.get("/orders", controller);
```

Spring:

```text
Request
  |
  v
Security Filter Chain
  |
  v
Security filters
  |
  v
Controller
```

But Spring Security's chain is a structured security pipeline with many framework-managed filters.

# 5. Defining SecurityFilterChain

Modern Spring Security configuration commonly uses a `SecurityFilterChain` bean.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            JwtAuthenticationFilter jwtAuthenticationFilter
    ) throws Exception {

        http
            .csrf(csrf -> csrf.disable())

            .sessionManagement(session ->
                session.sessionCreationPolicy(
                    SessionCreationPolicy.STATELESS
                )
            )

            .authorizeHttpRequests(auth -> auth
                .requestMatchers(
                    "/auth/login",
                    "/auth/register"
                ).permitAll()

                .requestMatchers("/admin/**")
                .hasRole("ADMIN")

                .requestMatchers("/orders/**")
                .hasAnyRole("USER", "ADMIN")

                .anyRequest()
                .authenticated()
            )

            .addFilterBefore(
                jwtAuthenticationFilter,
                UsernamePasswordAuthenticationFilter.class
            );

        return http.build();
    }
}
```

This configuration answers several important questions:

### Which endpoints are public?

```java
.requestMatchers("/auth/login", "/auth/register")
.permitAll()
```

### Which endpoints require a role?

```java
.requestMatchers("/admin/**")
.hasRole("ADMIN")
```

### What happens to everything else?

```java
.anyRequest()
.authenticated()
```

### Where does our custom JWT filter run?

```java
.addFilterBefore(
    jwtAuthenticationFilter,
    UsernamePasswordAuthenticationFilter.class
)
```

# 6. Filter Ordering

Spring Security creates and manages a chain of filters.

You can position a custom filter relative to an existing filter.

```java
.addFilterBefore(myFilter, SomeExistingFilter.class)
```

```java
.addFilterAfter(myFilter, SomeExistingFilter.class)
```

```java
.addFilterAt(myFilter, SomeExistingFilter.class)
```

For example:

```java
.addFilterBefore(
    jwtAuthenticationFilter,
    UsernamePasswordAuthenticationFilter.class
)
```

means:

```text
JwtAuthenticationFilter
        |
        v
UsernamePasswordAuthenticationFilter
```

The exact complete filter list depends on your Spring Security configuration/version. Do not memorize one universal order.

To inspect the runtime chain:

```properties
logging.level.org.springframework.security=DEBUG
```

# 7. `OncePerRequestFilter`

A custom JWT filter commonly extends:

```java
OncePerRequestFilter
```

Example:

```java
@Component
public class JwtAuthenticationFilter
        extends OncePerRequestFilter {

    private final JwtService jwtService;

    public JwtAuthenticationFilter(JwtService jwtService) {
        this.jwtService = jwtService;
    }

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain
    ) throws ServletException, IOException {

        String header =
            request.getHeader("Authorization");

        if (header == null ||
            !header.startsWith("Bearer ")) {

            filterChain.doFilter(request, response);
            return;
        }

        String token = header.substring(7);

        if (jwtService.isValid(token)) {

            String userId =
                jwtService.extractUserId(token);

            Authentication authentication =
                new UsernamePasswordAuthenticationToken(
                    userId,
                    null,
                    authorities
                );

            SecurityContextHolder
                .getContext()
                .setAuthentication(authentication);
        }

        filterChain.doFilter(request, response);
    }
}
```

The important line:

```java
filterChain.doFilter(request, response);
```

means:

> Continue to the remaining filters in the chain.

This is conceptually similar to Express:

```javascript
next();
```

If you don't call it, the request does not continue down the chain.

# 8. Does the Login Request Go Through the Filter Chain?

**Yes.**

If you have:

```text
POST /auth/login
```

the request still enters Spring Security's filter chain.

A typical custom REST login flow is:

```text
HTTP Request
     |
     v
SecurityFilterChain
     |
     v
/auth/login is permitAll
     |
     v
DispatcherServlet
     |
     v
AuthController
     |
     v
AuthenticationManager
```

Your JWT filter may run, but there is normally no JWT on the login request.

It therefore does:

```java
if (authorization == null) {
    filterChain.doFilter(request, response);
    return;
}
```

Then the request continues to the controller.

# 9. `AuthenticationManager`

`AuthenticationManager` is the main authentication abstraction.

Conceptually:

```java
public interface AuthenticationManager {

    Authentication authenticate(
        Authentication authentication
    ) throws AuthenticationException;
}
```

Its job is:

> Take an authentication request and attempt to authenticate it.

A common implementation is:

```text
ProviderManager
```

So:

```text
AuthenticationManager
        |
        v
ProviderManager
        |
        v
AuthenticationProvider(s)
```

# 10. `ProviderManager`

`ProviderManager` is a common `AuthenticationManager` implementation.

It maintains a collection of authentication providers.

Conceptually:

```text
ProviderManager
      |
      +--> DaoAuthenticationProvider
      |
      +--> JwtAuthenticationProvider
      |
      +--> LdapAuthenticationProvider
      |
      +--> CustomAuthenticationProvider
```

Multiple providers can exist in one Spring Boot application.

# 11. AuthenticationProvider

The core interface is:

```java
public interface AuthenticationProvider {

    Authentication authenticate(
        Authentication authentication
    ) throws AuthenticationException;

    boolean supports(Class<?> authentication);
}
```

### `supports()`

Answers:

> Can I handle this type of Authentication?

### `authenticate()`

Performs the actual authentication.

# 13. How does Spring choose a Provider?

The key method is:

```java
boolean supports(Class<?> authentication)
```

For example:

```java
@Override
public boolean supports(Class<?> authentication) {
    return UsernamePasswordAuthenticationToken.class
        .isAssignableFrom(authentication);
}
```

Conceptually:

```text
Authentication request
        |
        v
What Authentication type is this?
        |
        +--> UsernamePasswordAuthenticationToken
        |          |
        |          v
        |    DaoAuthenticationProvider
        |
        +--> BearerTokenAuthenticationToken
                   |
                   v
           JwtAuthenticationProvider
```

If multiple providers support the same authentication type, `ProviderManager` coordinates them according to its configured provider ordering and authentication behavior.

# 14. `UsernamePasswordAuthenticationToken`

The name is misleading if you are new to Spring Security.

It is an implementation of:

```text
Authentication
```

It does **not** mean your JWT must contain a username.

It can represent different stages.

## Before authentication

```java
new UsernamePasswordAuthenticationToken(
    email,
    password
);
```

Conceptually:

```text
principal   = email
credentials = password
authenticated = false
```

This means:

> "Here are my credentials. Please authenticate me."

## After successful authentication

```java
new UsernamePasswordAuthenticationToken(
    principal,
    null,
    authorities
);
```

Conceptually:

```text
principal   = authenticated user
credentials = null
authorities = ROLE_USER
authenticated = true
```

The first field is the **principal**, not necessarily a username.

The principal can be:

```text
String userId
UserDetails
CustomUserPrincipal
```

etc.

# 15. JWT Does Not Have to Contain a Username

For example:

```json
{
  "sub": "user-123",
  "tenantId": "tenant-456",
  "exp": 1900000000
}
```

The application can extract:

```text
user-123
```

and use it as the principal.

Or create:

```java
CustomUserPrincipal principal =
    new CustomUserPrincipal(
        userId,
        tenantId
    );
```

Then:

```java
Authentication authentication =
    new UsernamePasswordAuthenticationToken(
        principal,
        null,
        authorities
    );
```

There is no requirement that a JWT contain a `username` claim.

`Authentication` represents the security identity associated with the current authentication operation/request.

Conceptually:

```text
Authentication
├── principal
├── credentials
├── authorities
└── authenticated
```

Example:

```java
Authentication authentication =
    SecurityContextHolder
        .getContext()
```

Then:

```java
authentication.getPrincipal();
authentication.getAuthorities();
authentication.isAuthenticated();
```

# 17. SecurityContext

Spring Security maintains a `SecurityContext`.

Conceptually:

```text
SecurityContext
       |
       v
Authentication
       |
       +--> principal
       +--> authorities
       +--> authenticated
```

The current authentication can be accessed through:

```java
SecurityContextHolder
    .getContext()
    .getAuthentication();
```

In a stateless JWT application, the authentication is reconstructed for each request from the JWT.

It is not a permanent server-side login session.

# 18. Why Put Authentication in SecurityContext?

Suppose the JWT filter validates:

```text
JWT
 ↓
user-123
 ↓
ROLE_USER
```

It creates:

```java
Authentication authentication =
    new UsernamePasswordAuthenticationToken(
        "user-123",
        null,
        authorities
    );
```

Then:

```java
SecurityContextHolder
    .getContext()
    .setAuthentication(authentication);
```

Now downstream security infrastructure can ask:

```text
Who is making this request?
What authorities do they have?
```

The authorization layer can therefore enforce:

```java
.hasRole("ADMIN")
```

etc.

# 21. Password Verification

`UserDetailsService` does **not** verify the password.

It loads the user.

`DaoAuthenticationProvider` uses:

```text
PasswordEncoder
```

to verify the password.

Spring's abstraction:

```java
public interface PasswordEncoder {

    String encode(CharSequence rawPassword);

    boolean matches(
        CharSequence rawPassword,
        String encodedPassword
    );
}
```

Configure BCrypt:

```java
@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

Conceptually:

```text
raw password:
secret123

stored hash:
$2a$10$....

        |
        v

passwordEncoder.matches(
    "secret123",
    "$2a$10$..."
)

        |
        v

true / false
```

You do not decrypt a password hash.

---

# 22. Customizing Password Verification

If you genuinely need custom verification, you can implement `PasswordEncoder`:

```java
@Component
public class MyPasswordEncoder
        implements PasswordEncoder {

    @Override
    public String encode(
            CharSequence rawPassword
    ) {
        // custom encoding
    }

    @Override
    public boolean matches(
            CharSequence rawPassword,
            String encodedPassword
    ) {
        // custom verification
    }
}
```

Then `DaoAuthenticationProvider` can use your encoder.

However:

> Do not invent your own cryptographic password algorithm in a normal application.

Use established password hashing algorithms such as BCrypt, Argon2, PBKDF2, or SCrypt.

Custom `PasswordEncoder` implementations are more commonly useful for legacy compatibility or migrations.

# 23. Custom AuthenticationProvider

If you don't just want a different password hash but want a completely different authentication mechanism, implement:

```java
AuthenticationProvider
```

Example:

```java
@Component
public class OtpAuthenticationProvider
        implements AuthenticationProvider {

    @Override
    public Authentication authenticate(
            Authentication authentication) {

        OtpAuthenticationToken token =
            (OtpAuthenticationToken) authentication;

        // validate OTP

        if (!isValid(token)) {
            throw new BadCredentialsException(
                "Invalid OTP"
            );
        }

        return new UsernamePasswordAuthenticationToken(
            token.getPrincipal(),
            null,
            authorities
        );
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return OtpAuthenticationToken.class
            .isAssignableFrom(authentication);
    }
}
```

This gives you:

```text
AuthenticationManager
        |
        +--> DaoAuthenticationProvider
        |
        +--> OtpAuthenticationProvider
```

# 33. JwtService

This is **our application's service**, not a Spring Security magic class.

Example using JJWT:

```java
@Service
public class JwtService {

    private final SecretKey secretKey;

    public JwtService(SecretKey secretKey) {
        this.secretKey = secretKey;
    }

    public String generateToken(
            Authentication authentication
    ) {

        CustomUserDetails user =
            (CustomUserDetails)
                authentication.getPrincipal();

        return Jwts.builder()
            .subject(user.getUsername())
            .claim(
                "role",
                user.getAuthorities()
                    .iterator()
                    .next()
                    .getAuthority()
            )
            .issuedAt(new Date())
            .expiration(
                new Date(
                    System.currentTimeMillis()
                    + 15 * 60 * 1000
                )
            )
            .signWith(secretKey)
            .compact();
    }

    public String extractSubject(String token) {

        return Jwts.parser()
            .verifyWith(secretKey)
            .build()
            .parseSignedClaims(token)
            .getPayload()
            .getSubject();
    }

    public boolean isValid(String token) {

        try {

            Jwts.parser()
                .verifyWith(secretKey)
                .build()
                .parseSignedClaims(token);

            return true;

        } catch (JwtException |
                 IllegalArgumentException e) {

            return false;
        }
    }
}
```

For a real production implementation, keep the secret/key outside source code and use appropriate key management/configuration.

# 34. JwtAuthenticationFilter

```java
@Component
public class JwtAuthenticationFilter
        extends OncePerRequestFilter {

    private final JwtService jwtService;

    public JwtAuthenticationFilter(
            JwtService jwtService
    ) {
        this.jwtService = jwtService;
    }

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain
    ) throws ServletException, IOException {

        String authorization =
            request.getHeader("Authorization");

        if (authorization == null ||
            !authorization.startsWith("Bearer ")) {

            filterChain.doFilter(request, response);
            return;
        }

        String token =
            authorization.substring(7);

        if (!jwtService.isValid(token)) {
            filterChain.doFilter(request, response);
            return;
        }

        String subject =
            jwtService.extractSubject(token);

        Authentication authentication =
            new UsernamePasswordAuthenticationToken(
                subject,
                null,
                List.of(
                    new SimpleGrantedAuthority(
                        "ROLE_USER"
                    )
                )
            );

        SecurityContextHolder
            .getContext()
            .setAuthentication(authentication);

        filterChain.doFilter(request, response);
    }
}
```

### Important production note

This example is intentionally showing the mechanism.

In a real application, you should not blindly trust a role hardcoded as:

```java
ROLE_USER
```

You would derive authorities from trusted claims or load the user's authorization data according to your security architecture.

Also, Spring Security's built-in Resource Server JWT support is often preferable to maintaining a custom JWT filter yourself.

# 40. Stateless Sessions

Configure:

```java
.sessionManagement(session ->
    session.sessionCreationPolicy(
        SessionCreationPolicy.STATELESS
    )
)
```

Meaning:

> Spring Security should not use a server-side HTTP session as the authentication state for this API.

For each request:

```text
JWT
 ↓
validate
 ↓
Authentication
 ↓
SecurityContext
```

The context is request-scoped/lifecycle-managed, not a permanent login session.

# 41. Why Stateless Helps Horizontal Scaling

Suppose:

```text
             Load Balancer
             /     |     \
            /      |      \
       Server A Server B Server C
```

With server-side sessions:

```text
Session
  |
  v
Server A
```

A later request might reach Server B.

You then need mechanisms such as:

```text
sticky sessions
```

or:

```text
distributed session storage
```

With stateless JWT authentication:

```text
Client
  |
  | JWT
  v
Load Balancer
  |
  +--> Server A
  +--> Server B
  +--> Server C
```

Each server can validate the JWT using the appropriate verification key.

This simplifies horizontal scaling.

It does **not** mean the entire application has no shared infrastructure.

# 42. JWT Structure

```text
HEADER.PAYLOAD.SIGNATURE
```

Example:

```json
Header:
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Payload:

```json
{
  "sub": "user-123",
  "role": "USER",
  "iat": 1900000000,
  "exp": 1900000900
}
```

Signature:

```text
sign(
    base64Url(header)
    + "."
    + base64Url(payload),
    signingKey
)
```

JWT signing provides integrity/authenticity properties.

It does **not** mean the payload is encrypted.

Do not put passwords or sensitive secrets into ordinary JWT claims.

# 44. JWT Signature vs Encryption

Signed JWT:

```text
"I can verify that this token was signed
by a trusted issuer and wasn't modified."
```

Not:

```text
"Nobody can read the payload."
```

Anyone who possesses the token can normally decode its payload.

If confidentiality is required, use appropriate encryption mechanisms rather than assuming normal signed JWTs provide it.

```text

    |

    +--> sent to APIs

    |
    +--> longer-lived
```

# 48. CSRF

CSRF:

```text
Cross-Site Request Forgery
```

It matters especially when authentication credentials are automatically attached by the browser, such as cookies.

If your API uses:

```http
Authorization: Bearer <JWT>
```

and the browser only sends that header when your application explicitly adds it, traditional cookie-based CSRF attacks don't apply in the same way.

But:

> "JWT means CSRF can always be disabled"

is too simplistic.

If your JWT is stored in an automatically sent cookie, CSRF considerations return.

The real question is:

> How is the credential stored and automatically transmitted?

```text
CORS
    ->
Which origins can browser JavaScript
make/read cross-origin requests from?

CSRF
    ->
Can an attacker cause an authenticated
user's browser to perform an unwanted action?
```

They solve different problems.


# 53. Interview Questions

## Q1. Explain Spring Security authentication.

Strong answer:

> During login, the client submits credentials. The request passes through the Spring Security filter chain and reaches the login endpoint because that endpoint is configured as `permitAll`. The controller creates an authentication request, commonly a `UsernamePasswordAuthenticationToken`, and passes it to `AuthenticationManager`. A `ProviderManager` delegates it to a suitable `AuthenticationProvider`, commonly `DaoAuthenticationProvider`. The provider loads the user through `UserDetailsService`, verifies the password through `PasswordEncoder`, and returns an authenticated `Authentication` object. The application can then create a signed JWT and return it to the client.

---

## Q2. What is UserDetailsService?

> It is an abstraction used by Spring Security to load user security information during username/password authentication. The application commonly implements it to retrieve a user from its database and convert that user into `UserDetails`. It does not itself verify the password.

---

## Q3. Who verifies the password?

> `DaoAuthenticationProvider` coordinates username/password authentication and uses the configured `PasswordEncoder` to verify the submitted raw password against the stored encoded password.

---

## Q4. Can we customize password verification?

> Yes. We can provide a custom `PasswordEncoder` implementation, although in normal applications we should use established password hashing algorithms rather than inventing our own cryptography.

---

## Q5. Can one application have multiple AuthenticationProviders?

> Yes. A `ProviderManager` can coordinate multiple providers. Providers advertise which `Authentication` types they support through `supports()`. For example, an application could use `DaoAuthenticationProvider` for username/password login and JWT-related authentication for bearer tokens, or have a custom provider for OTP authentication.

---

## Q6. Does JWT have to contain a username?

> No. JWT contains claims chosen by the application/issuer. The principal can be identified by a user ID, account ID, subject, or another claim. `UsernamePasswordAuthenticationToken` is an `Authentication` implementation; its principal does not have to literally be a username.

---

## Q7. Where is JWT validated?

> In the Spring Security request-processing pipeline. With Spring Security's Resource Server JWT support, bearer-token processing is handled by `BearerTokenAuthenticationFilter`, which delegates JWT authentication to the JWT authentication provider and decoder/validators. With a custom implementation, a custom filter can extract and validate the token before establishing the `Authentication` in the `SecurityContext`.

---

## Q8. Where do we define which endpoints require authentication?

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/auth/login").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated()
)
```

---

## Q9. Where do we define filter ordering?

```java
.addFilterBefore(...)
.addFilterAfter(...)
.addFilterAt(...)
```

For example:

```java
.addFilterBefore(
    jwtAuthenticationFilter,
    UsernamePasswordAuthenticationFilter.class
)
```

---

## Q10. What is SecurityContext?

> `SecurityContext` holds the `Authentication` associated with the current security execution/request. After JWT authentication succeeds, Spring Security places the resulting `Authentication` into the security context so downstream authorization and application code can determine the current principal and authorities.

---

## Q11. Authentication vs Authorization?

```text
Authentication = Who are you?
Authorization  = What are you allowed to do?
```

---

## Q12. Why stateless JWT?

> With stateless authentication, the application doesn't need to maintain a per-user authentication session between requests. Each request carries credentials such as a bearer token that can be independently validated, making horizontal scaling simpler.

---
