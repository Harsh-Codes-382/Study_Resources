# 3.5 Transactions — Spring Interview Prep

## Goal

Understand Spring transactions well enough to explain:

- What `@Transactional` does
- Why `@Transactional` is implemented through AOP/proxies
- Propagation: `REQUIRED`, `REQUIRES_NEW`, `NESTED`, `SUPPORTS`, etc.
- Isolation levels
- Rollback rules
- `readOnly`
- The self-invocation/proxy gotcha
- Why `this.method()` bypasses the Spring proxy
- The important difference between "the method's own `@Transactional` is not applied" and "there is no transaction at all"

---

# 1. What is a transaction?

A transaction is a group of database operations that should behave as one logical unit of work.

A classic example is transferring money:

```java
// Account A: ₹1000
// Account B: ₹500

deduct ₹200 from A;
add ₹200 to B;
```

We want either:

```text
A = ₹800
B = ₹700
```

or, if something fails:

```text
A = ₹1000
B = ₹500
```

We do NOT want:

```text
A = ₹800
B = ₹500
```

because money would effectively disappear.

Conceptually:

```text
BEGIN TRANSACTION

    deduct money
    add money

COMMIT
```

If something fails:

```text
BEGIN TRANSACTION

    deduct money
    add money  <-- failure

ROLLBACK
```

So the basic idea is:

> A transaction groups related database operations so they can be committed together or rolled back together.

# 2. What does `@Transactional` mean?

Example:

```java
@Service
public class PaymentService {

    @Transactional
    public void transferMoney() {

        accountRepository.debit(200);
        accountRepository.credit(200);
    }
}
```

`@Transactional` tells Spring that this method should participate in transaction management.

A very important point:

> `@Transactional` is not itself a database transaction implementation.

Spring normally applies it using AOP/proxy-based transaction management.

Conceptually:

```text
Caller
   |
   v
Spring Proxy
   |
   | BEGIN TRANSACTION
   v
Real Service Object
   |
   | execute method
   |
   v
Spring Proxy
   |
   | COMMIT / ROLLBACK
   v
Database
```

---

# 3. The proxy mental model

Suppose:

```java
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
    }
}
```

You can mentally imagine Spring as having:

```text
OrderService Proxy
       |
       v
Actual OrderService
```

The proxy is responsible for intercepting the method call.

Conceptually, the proxy does something like:

```java
public void placeOrder(Order order) {

    transactionManager.begin();

    try {
        target.placeOrder(order);

        transactionManager.commit();

    } catch (RuntimeException e) {

        transactionManager.rollback();

        throw e;
    }
}
```

This is conceptual code, not Spring's exact internal implementation.

The important idea is:

> The proxy surrounds the actual method call with transaction management.

---

# 4. Why does calling from a Controller work?

Suppose:

```java
@RestController
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping("/orders")
    public void createOrder(Order order) {
        orderService.placeOrder(order);
    }
}
```

And:

```java
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
    }
}
```

The call is conceptually:

```text
Controller
    |
    | orderService.placeOrder()
    v
OrderService Proxy
    |
    | BEGIN TRANSACTION
    v
Actual OrderService
    |
    | placeOrder()
    v
COMMIT
```

So YES, a transaction starts.

Why?

Because the Controller is calling the Spring-managed `OrderService` bean from outside the service object.

The call goes through the proxy.

# 5. The self-invocation problem

This is one of the most important Spring interview topics.

Consider:

```java
@Service
public class OrderService {

    public void placeOrder() {

        System.out.println("place order");

        saveOrder();
    }

    @Transactional
    public void saveOrder() {

        orderRepository.save(...);
    }
}
```

Suppose the Controller calls:

```java
orderService.placeOrder();
```

The first call does go through the proxy:

```text
Controller
    |
    v
OrderService Proxy
    |
    v
placeOrder()
```

So far, everything is fine.

But inside `placeOrder()`:

```java
saveOrder();
```

is effectively:

```java
this.saveOrder();
```

Now the important part:

```text
Controller
    |
    v
OrderService Proxy
    |
    v
placeOrder()
    |
    | this.saveOrder()
    v
saveOrder()
```

The `this.saveOrder()` call goes directly to the same object.

It does NOT go back through:

```text
OrderService Proxy
```

Therefore the transaction interceptor doesn't get another chance to apply the `@Transactional` annotation on `saveOrder()`.

---

# 6. Exact rule for self-invocation

Remember this:

> Self-invocation bypasses the Spring proxy.

Therefore:

```java
this.saveOrder();
```

does NOT cause Spring to intercept `saveOrder()`.

So this:

```java
@Transactional
public void saveOrder() {
}
```

does not automatically start a transaction when called internally as:

```java
this.saveOrder();
```

---

# 7. Very important nuance: "No transaction" vs "no transaction from this annotation"

This distinction is extremely important.

Consider:

```java
@Service
public class OrderService {

    public void placeOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        orderRepository.save(...);
    }
}
```

If `placeOrder()` itself is NOT transactional:

```text
Controller
    |
    v
Proxy
    |
    v
placeOrder()
    |
    | this.saveOrder()
    v
saveOrder()
```

Then `saveOrder()`'s own `@Transactional` is not applied.

So, assuming there was no transaction already:

```text
No transaction started by saveOrder()
```

This is the example where saying:

> "The `@Transactional` annotation on `saveOrder()` does not work because self-invocation bypasses the proxy."

is correct.

---

# 8. But what if the outer method is transactional?

Now change the code:

```java
@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        orderRepository.save(...);
    }
}
```

Controller calls:

```java
orderService.placeOrder();
```

Flow:

```text
Controller
    |
    v
OrderService Proxy
    |
    | BEGIN TRANSACTION
    v
placeOrder()
    |
    | this.saveOrder()
    v
saveOrder()
```

The `saveOrder()` call still bypasses the proxy.

BUT there is already a transaction because `placeOrder()` started one.

Therefore `saveOrder()` executes inside the existing transaction.

This gives a very important interview statement:

> Self-invocation prevents the transactional annotation on the called method from being intercepted, but it does not necessarily mean that no transaction exists. An outer transaction may already be active.

# 9. Two cases you should memorize

## Case A — outer method is NOT transactional

```java
public void placeOrder() {
    saveOrder();
}

@Transactional
public void saveOrder() {
    repository.save(...);
}
```

Flow:

```text
Controller
   |
   v
Proxy
   |
   v
placeOrder()
   |
   | this.saveOrder()
   v
saveOrder()
```

Result:

```text
saveOrder()'s @Transactional
        ↓
   NOT intercepted
        ↓
No transaction started by this annotation
```

---

## Case B — outer method IS transactional

```java
@Transactional
public void placeOrder() {
    saveOrder();
}

@Transactional
public void saveOrder() {
    repository.save(...);
}
```

Flow:

```text
Controller
   |
   v
Proxy
   |
   | BEGIN T1
   v
placeOrder()
   |
   | this.saveOrder()
   v
saveOrder()
   |
   | uses existing T1
   v
repository
```

Result:

```text
T1 already exists
        ↓
saveOrder() runs inside T1
```

The inner annotation itself wasn't intercepted, but the method still runs within the outer transaction.

# 10. Propagation

Propagation answers:

> What should happen when a transactional method calls another transactional method?

For example:

```java
@Transactional
public void outer() {
    inner();
}

@Transactional
public void inner() {
}
```

Should `inner()`:

- join the existing transaction?
- create a new transaction?
- run without a transaction?
- use a savepoint?

Propagation controls this behavior.

---

# 11. `REQUIRED`

`REQUIRED` is the default propagation.

```java
@Transactional(propagation = Propagation.REQUIRED)
public void method() {
}
```

Meaning:

> If a transaction already exists, join it. Otherwise, create a new transaction.

Conceptually:

```text
Transaction exists?
       |
   +---+---+
   |       |
  YES      NO
   |       |
 JOIN    CREATE
```

Example:

```java
@Transactional
public void outer() {
    inner();
}

@Transactional
public void inner() {
    // database work
}
```

Normally:

```text
BEGIN T1

outer()
   |
   +--> inner()

COMMIT T1
```

There is one logical transaction.

---

# 12. Why `REQUIRED` is the default

Imagine:

```java
@Transactional
public void placeOrder() {

    createOrder();

    decreaseInventory();

    createPayment();
}
```

You usually want all operations to succeed or all to roll back.

If:

```text
createOrder       ✓
decreaseInventory ✓
createPayment     ✗
```

then:

```text
ROLLBACK
```

This is exactly the behavior that `REQUIRED` naturally supports when these operations participate in the same transaction.

---

# 13. `REQUIRES_NEW`

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void inner() {
}
```

Meaning:

> Always use a new transaction.

If an outer transaction exists:

1. Suspend the outer transaction.
2. Start a new transaction.
3. Execute the inner method.
4. Commit or roll back the inner transaction independently.
5. Resume the outer transaction.

Conceptually:

```text
T1
 |
 | SUSPEND
 v
T2
 |
 | COMMIT / ROLLBACK
 v
Resume T1
```

---

# 14. REQUIRED vs REQUIRES_NEW — outer fails, inner commits

This is an important interview example.

Outer:

```java
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {

        orderRepository.save(order);

        auditService.log("Order created");

        throw new RuntimeException("Payment failed");
    }
}
```

Audit:

```java
@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(String message) {

        auditRepository.save(message);
    }
}
```

Execution:

```text
T1 starts
 |
 | save order
 |
 | call auditService.log()
 |
 | T1 SUSPENDED
 |
 v
T2 starts
 |
 | save audit
 |
 | T2 COMMIT
 |
 v
T1 RESUMED
 |
 | RuntimeException
 |
 v
T1 ROLLBACK
```

Final state:

```text
Order → ROLLED BACK
Audit → COMMITTED
```

This is the classic:

> "Outer transaction fails, but the inner `REQUIRES_NEW` transaction has already committed."

---

# 15. Why is `REQUIRES_NEW` useful?

A common example is audit logging.

Suppose:

```java
@Transactional
public void processPayment() {

    paymentRepository.save(payment);

    auditService.log("Payment started");

    // payment processing fails
}
```

If audit uses `REQUIRED`, the audit participates in the same transaction.

If the outer transaction rolls back:

```text
Payment → rollback
Audit   → rollback
```

With `REQUIRES_NEW`:

```text
Payment transaction T1
       |
       | suspend
       v
Audit transaction T2
       |
       | commit
       v
Resume T1
       |
       | rollback
       v
Payment → rollback
Audit   → committed
```

Important nuance:

`REQUIRES_NEW` uses an independent physical transaction, so the application may need another database connection while the outer transaction is suspended.

---

# 16. `NESTED`

```java
@Transactional(propagation = Propagation.NESTED)
public void inner() {
}
```

Think:

> Nested work using a savepoint inside the existing transaction.

Conceptually:

```text
T1
 |
 | operation A
 |
 | SAVEPOINT
 |
 | operation B
 |
 | rollback to SAVEPOINT
 |
 | operation C
 |
 COMMIT
```

Compare:

```text
REQUIRES_NEW
-------------------------
T1 suspended
T2 starts
T2 commits independently
T1 resumes
```

versus:

```text
NESTED
-------------------------
T1 continues
SAVEPOINT
nested work
rollback to SAVEPOINT if needed
T1 continues
```

Interview sentence:

> `REQUIRES_NEW` creates an independent transaction, whereas `NESTED` uses a savepoint within an existing transaction when supported by the transaction infrastructure/database.

---

# 17. `SUPPORTS`

```java
@Transactional(propagation = Propagation.SUPPORTS)
```

Meaning:

> If a transaction exists, join it. If there is no transaction, execute without one.

```text
Existing transaction?
       |
   +---+---+
   |       |
  YES      NO
   |       |
 JOIN    NO TX
```

---

# 18. `MANDATORY`

```java
Propagation.MANDATORY
```

Meaning:

> A transaction must already exist.

If one exists:

```text
JOIN
```

If one doesn't:

```text
Exception
```

---

# 19. `NOT_SUPPORTED`

```java
Propagation.NOT_SUPPORTED
```

Meaning:

> Execute without a transaction.

If a transaction already exists, Spring suspends it.

```text
T1
 |
 | SUSPEND
 v
No transaction
 |
 | execute
 v
Resume T1
```

---

# 20. `NEVER`

```java
Propagation.NEVER
```

Meaning:

> A transaction must NOT exist.

If a transaction exists, the operation fails.

---

# 21. Propagation summary

| Propagation | Existing transaction | Behavior |
|---|---|---|
| `REQUIRED` | Yes | Join it |
| `REQUIRED` | No | Create one |
| `REQUIRES_NEW` | Yes | Suspend it and create a new one |
| `REQUIRES_NEW` | No | Create one |
| `NESTED` | Yes | Use a nested/savepoint-style transaction |
| `SUPPORTS` | Yes | Join it |
| `SUPPORTS` | No | No transaction |
| `MANDATORY` | Yes | Join it |
| `MANDATORY` | No | Exception |
| `NOT_SUPPORTED` | Yes | Suspend it |
| `NOT_SUPPORTED` | No | No transaction |
| `NEVER` | Yes | Exception |
| `NEVER` | No | No transaction |

For most interviews, prioritize:

```text
REQUIRED
REQUIRES_NEW
NESTED
```

# 22. Isolation

Propagation answers:

> Which transaction should I participate in?

Isolation answers:

> How isolated should concurrent transactions be from each other?

Imagine two transactions:

```text
Transaction A
Transaction B
```

running at the same time.

Isolation determines what one transaction is allowed to observe from another.

---

# 23. Dirty read

Transaction A changes data but has not committed:

```text
A:
balance 100 → 50
```

Transaction B reads:

```text
balance = 50
```

Then A rolls back:

```text
balance = 100
```

B saw data that was never committed.

This is a:

> Dirty read.

---

# 24. Non-repeatable read

Transaction A reads:

```text
balance = 100
```

Transaction B changes it and commits:

```text
balance = 50
```

Transaction A reads again:

```text
balance = 50
```

The same transaction got different values for the same row.

This is a:

> Non-repeatable read.

---

# 25. Phantom read

Transaction A executes:

```sql
SELECT * FROM orders
WHERE amount > 1000;
```

It gets:

```text
5 rows
```

Transaction B inserts another matching row and commits.

Transaction A executes the query again:

```text
6 rows
```

The additional row is a:

> Phantom row.

---

# 26. Spring isolation levels

You can specify:

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
```

Common levels:

```text
DEFAULT
READ_UNCOMMITTED
READ_COMMITTED
REPEATABLE_READ
SERIALIZABLE
```

## `DEFAULT`

Use the database's default isolation level.

## `READ_UNCOMMITTED`

Lowest standard isolation.

Dirty reads can occur.

## `READ_COMMITTED`

Reads only committed data.

Typically prevents dirty reads.

## `REPEATABLE_READ`

Provides stronger consistency for rows already read.

Typically prevents dirty and non-repeatable reads.

Exact behavior, especially around phantoms, depends on the database implementation.

## `SERIALIZABLE`

Strongest standard isolation level.

Transactions behave as though conflicting operations were serialized.

It can reduce concurrency and increase locking/contention.

Important:

> Spring declares the desired isolation level; the underlying database/transaction infrastructure enforces its actual semantics.

# 27. Rollback rules

By default, Spring rolls back for:

```text
RuntimeException
Error
```

These are unchecked exceptions/errors.

Example:

```java
@Transactional
public void saveOrder() {

    repository.save(order);

    throw new RuntimeException("Failed");
}
```

Conceptually:

```text
BEGIN
 |
 | save
 |
 | RuntimeException
 |
 ROLLBACK
```

---

# 28. Checked exceptions

Consider:

```java
@Transactional
public void saveOrder() throws Exception {

    repository.save(order);

    throw new Exception("Failed");
}
```

`Exception` is a checked exception.

By default, Spring does not roll back just because this checked exception was thrown.

This is an important interview point:

> By default, Spring rolls back on unchecked exceptions, not checked exceptions.

---

# 29. `rollbackFor`

To make a checked exception trigger rollback:

```java
@Transactional(rollbackFor = Exception.class)
public void saveOrder() throws Exception {

    repository.save(order);

    throw new Exception();
}
```

Or preferably, when appropriate, specify the particular checked exception:

```java
@Transactional(rollbackFor = PaymentException.class)
```

Interview answer:

> Checked exceptions can be configured to trigger rollback using `rollbackFor`.

---

# 30. `noRollbackFor`

You can also explicitly say an exception should not cause rollback:

```java
@Transactional(
    noRollbackFor = BusinessWarningException.class
)
public void process() {
}
```

So transaction behavior can be customized with:

```text
rollbackFor
noRollbackFor
```

---

# 31. Important exception-handling trap

Consider:

```java
@Transactional
public void process() {

    try {
        repository.save(order);

        throw new RuntimeException("Failed");

    } catch (RuntimeException e) {

        System.out.println("Handled");
    }
}
```

The exception is caught inside the transactional method.

From the transaction interceptor's point of view, the method may return normally.

Therefore, you should NOT assume that the transaction will automatically roll back just because a `RuntimeException` occurred somewhere inside the method.

Important interview concept:

> Spring's rollback decision is made at the transactional boundary. If you catch an exception inside the method and don't otherwise mark the transaction for rollback, the interceptor may see normal method completion and commit.

---

# 32. `readOnly`

Example:

```java
@Transactional(readOnly = true)
public User getUser(Long id) {

    return userRepository.findById(id)
            .orElseThrow();
}
```

`readOnly = true` communicates:

> This transaction is intended for reading rather than modifying data.

It can allow Spring/JPA/Hibernate/database infrastructure to optimize certain behavior.

But do NOT say:

> "`readOnly = true` makes writes impossible."

That's too strong.

Better interview answer:

> "`readOnly` is a hint to the transaction infrastructure and underlying persistence technology that the transaction is intended for reads. The exact effect depends on the persistence provider and database."

---

# 33. Full proxy example

Consider:

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final AuditService auditService;

    public OrderService(
            OrderRepository orderRepository,
            AuditService auditService) {

        this.orderRepository = orderRepository;
        this.auditService = auditService;
    }

    @Transactional
    public void placeOrder(Order order) {

        orderRepository.save(order);

        auditService.log("Order created");

        throw new RuntimeException("Payment failed");
    }
}
```

Controller:

```java
@RestController
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    public void createOrder(Order order) {
        orderService.placeOrder(order);
    }
}
```

The flow is:

```text
Controller
    |
    v
OrderService Proxy
    |
    | BEGIN T1
    v
placeOrder()
    |
    +--> save order
    |
    +--> auditService.log()
    |
    +--> RuntimeException
    |
    v
ROLLBACK T1
```

So there IS a transaction.

The controller's call goes through the proxy.

# 34. Full `REQUIRES_NEW` example

```java
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {

        orderRepository.save(order);

        auditService.log("Order created");

        throw new RuntimeException("Payment failed");
    }
}
```

Audit:

```java
@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(String message) {

        auditRepository.save(message);
    }
}
```

Flow:

```text
OrderService Proxy
       |
       | BEGIN T1
       v
placeOrder()
       |
       +--> save order
       |
       +--> AuditService Proxy
                    |
                    | SUSPEND T1
                    |
                    | BEGIN T2
                    v
                  log()
                    |
                    | COMMIT T2
                    |
                    v
                 RESUME T1
       |
       +--> RuntimeException
       |
       v
ROLLBACK T1
```

Final state:

```text
Order → rolled back
Audit → committed
```

# 35. The most important self-invocation example

## Problem

```java
@Service
public class OrderService {

    public void placeOrder() {

        System.out.println("place order");

        saveOrder();
    }

    @Transactional
    public void saveOrder() {

        orderRepository.save(...);
    }
}
```

Controller:

```java
orderService.placeOrder();
```

Flow:

```text
Controller
    |
    v
OrderService Proxy
    |
    v
placeOrder()
    |
    | this.saveOrder()
    v
saveOrder()
```

The first call went through the proxy.

The second call did NOT.

Therefore:

```text
saveOrder()'s @Transactional
            ↓
       proxy bypassed
            ↓
     not intercepted
```

If no transaction already exists:

```text
No transaction started by saveOrder()
```

---

# 36. The fix: move the transactional method to another bean

Instead of:

```java
@Service
public class OrderService {

    public void placeOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
    }
}
```

Use:

```java
@Service
public class OrderService {

    private final OrderWriter orderWriter;

    public OrderService(OrderWriter orderWriter) {
        this.orderWriter = orderWriter;
    }

    public void placeOrder() {
        orderWriter.saveOrder();
    }
}
```

And:

```java
@Service
public class OrderWriter {

    @Transactional
    public void saveOrder() {
        orderRepository.save(...);
    }
}
```

Now:

```text
OrderService
     |
     v
OrderWriter Proxy
     |
     | BEGIN TRANSACTION
     v
OrderWriter.saveOrder()
     |
     v
COMMIT
```

The call crosses a Spring bean/proxy boundary.

This is usually the cleanest solution.

# 37. Interview questions and answers

## Q1. What is `@Transactional`?

Answer:

> "`@Transactional` is Spring's declarative transaction-management mechanism. It is typically implemented using AOP proxies. The proxy starts or joins a transaction before invoking the target method and then commits or rolls back based on the transaction outcome."

---

## Q2. What is the default propagation?

Answer:

> "`REQUIRED`."

Then explain:

> "It joins an existing transaction if one exists; otherwise it creates a new transaction."

---

## Q3. REQUIRED vs REQUIRES_NEW?

Answer:

> "`REQUIRED` joins the existing transaction or creates one if necessary. `REQUIRES_NEW` always creates an independent transaction, suspending the existing transaction if there is one."

---

## Q4. Give an example where outer fails but inner commits.

Answer:

> "An outer `placeOrder()` method runs in T1 and calls an audit method using `REQUIRES_NEW`. Spring suspends T1, starts T2, and commits the audit. T1 is then resumed and later rolls back because the outer method throws a runtime exception. Therefore the order rolls back but the audit remains committed."

---

## Q5. What is the default rollback behavior?

Answer:

> "By default, Spring rolls back on unchecked exceptions such as `RuntimeException` and on `Error`. Checked exceptions do not trigger rollback by default. For checked exceptions, we can use `rollbackFor`."

---

## Q6. Why does self-invocation break `@Transactional`?

Answer:

> "Spring normally applies `@Transactional` through an AOP proxy. An external call goes through the proxy, but an internal call such as `this.saveOrder()` directly invokes the target object and bypasses the proxy. Therefore the transaction interceptor does not get invoked for the internally called method."

---

## Q7. Does self-invocation always mean there is no transaction?

Answer:

> "No. It means the called method's transactional annotation is not intercepted. If an outer method already started a transaction, the internally called method can still execute inside that existing transaction."

---

## Q8. What is `readOnly = true`?

Answer:

> "`readOnly` indicates that the transaction is intended for read operations. It can allow the persistence provider or database infrastructure to optimize certain behavior, but it should not be treated as a universal guarantee that writes are impossible."
