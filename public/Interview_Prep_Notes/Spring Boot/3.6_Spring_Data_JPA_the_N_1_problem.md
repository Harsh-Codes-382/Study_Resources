# JPA & Hibernate Interview Preparation

> **Purpose:** Interview revision notes for JPA, Hibernate, ORM concepts, relationships, fetching, N+1 queries, transactions, persistence context, caching, and common interview questions.

---

## 1. What is JPA?

**JPA (Jakarta Persistence API)** is a specification/API for mapping Java objects to relational database tables.

It defines concepts such as:

- Entities
- Entity relationships
- Persistence context
- Entity lifecycle
- JPQL
- Criteria API
- Transactions
- Fetching strategies
- Cascades
- Locking

JPA itself is **not an implementation**.

Common implementations:

- Hibernate
- EclipseLink
- OpenJPA

In most Spring Boot applications, **Hibernate is the JPA provider**.

### Mental model

```text
Java Object
    ↓
JPA annotations / API
    ↓
Hibernate (JPA implementation)
    ↓
JDBC
    ↓
Database
```

---

## 2. JPA vs Hibernate

| JPA | Hibernate |
|---|---|
| Specification | Implementation |
| Defines APIs and rules | Implements those rules |
| Vendor-neutral | Hibernate-specific features also exist |

A good interview answer:

> JPA is a specification for persistence/ORM in Java, while Hibernate is one of the most widely used implementations of that specification.

---

## 3. What is ORM?

**ORM = Object Relational Mapping**

It maps:

```text
Java class  → Database table
Java object → Database row
Field       → Column
Relationship → Foreign key / join table
```

Example:

```java
@Entity
public class User {

    @Id
    private Long id;

    private String name;
}
```

---

## 4. Entity

An entity is a Java class whose objects are persisted in a database.

```java
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue
    private Long id;

    private String name;
}
```

Important points:

- Use `@Entity`.
- Define an identifier with `@Id`.
- Provide a no-argument constructor.
- Entity classes should generally not be `final`.
- Persistent fields/properties map to database columns.

---

## 5. Entity Lifecycle

```text
             persist()
NEW ----------------------> MANAGED
                              |
                              | detach()
                              ↓
                           DETACHED
                              |
                              | merge()
                              ↓
                           MANAGED

MANAGED
   |
   | remove()
   ↓
REMOVED
```

### Transient / New

```java
User user = new User();
user.setName("Harsh");
```

The object exists only in Java and is not managed.

### Managed / Persistent

```java
entityManager.persist(user);
```

The entity is associated with the persistence context.

### Detached

The entity was previously managed but is no longer attached.

```java
entityManager.detach(user);
```

### Removed

```java
entityManager.remove(user);
```

The entity is marked for deletion.

---

## 6. Persistence Context

The persistence context is one of the most important JPA concepts.

Think of it as:

> A managed set of entity instances associated with an `EntityManager`, providing identity management, dirty checking, and first-level caching.

Example:

```java
User u1 = entityManager.find(User.class, 1L);
User u2 = entityManager.find(User.class, 1L);
```

Within the same persistence context, they normally refer to the same managed instance.

---

## 7. Dirty Checking

Hibernate automatically detects changes made to managed entities.

```java
@Transactional
public void updateUser(Long id) {

    User user = entityManager.find(User.class, id);

    user.setName("Updated");
}
```

At flush/commit, Hibernate can generate:

```sql
UPDATE users
SET name = 'Updated'
WHERE id = 1;
```

This is **dirty checking**.

---

## 8. Flush vs Commit

### Flush

Synchronizes pending persistence-context changes with the database.

```text
Persistence Context
       ↓ flush
Database
```

### Commit

Completes the database transaction.

```text
Transaction
    ↓
COMMIT
```

Important:

> **Flush does not mean commit.**

A flushed transaction can still be rolled back.

---

## 9. First-Level Cache

The first-level cache is associated with the persistence context and is enabled by default.

```java
User user1 = entityManager.find(User.class, 1L);
User user2 = entityManager.find(User.class, 1L);
```

The second lookup can use the already-managed entity rather than querying the database again.

```text
Persistence Context
 ┌──────────────────────┐
 │ User#1 → object      │
 │ User#2 → object      │
 └──────────────────────┘
```

---

## 10. Second-Level Cache

The second-level cache exists beyond a single persistence context and can be shared across sessions/entity managers.

Common integrations include:

- Ehcache
- Infinispan
- Other provider/cache integrations

It is optional.

```text
Application
    |
    +-- L1 Cache / Persistence Context
    |
    +-- L2 Cache
    |
    +-- Database
```

---

## 11. EntityManager

`EntityManager` is the main JPA API for interacting with the persistence context.

Common methods:

```java
persist(entity)
find(Entity.class, id)
merge(entity)
remove(entity)
detach(entity)
clear()
flush()
refresh(entity)
```

---

## 12. `persist()` vs `merge()`

### `persist()`

Used to make a new entity managed.

```java
entityManager.persist(user);
```

The supplied entity becomes managed.

### `merge()`

Used to copy the state of a detached entity into a managed entity.

```java
User managedUser = entityManager.merge(detachedUser);
```

Important:

```java
detachedUser != managedUser
```

The returned object is the managed instance.

### Interview trap

Do not say:

> `merge()` attaches the same object.

Better:

> `merge()` copies the state of the supplied entity into a managed entity and returns the managed instance.

---

## 13. `remove()`, `detach()`, `clear()`, `refresh()`

### `remove()`

```java
entityManager.remove(user);
```

Marks a managed entity for deletion.

### `detach()`

```java
entityManager.detach(user);
```

Removes one entity from the persistence context.

### `clear()`

```java
entityManager.clear();
```

Removes all managed entities from the persistence context.

### `refresh()`

```java
entityManager.refresh(user);
```

Reloads the entity's state from the database.

# Relationships

## 14. JPA Relationships

JPA supports:

- `@OneToOne`
- `@OneToMany`
- `@ManyToOne`
- `@ManyToMany`

---

## 15. Many-to-One

Example:

```text
Many Orders → One Customer
```

```java
@ManyToOne
@JoinColumn(name = "customer_id")
private Customer customer;
```

The foreign key is commonly stored on the `orders` table.

---

## 16. One-to-Many

```text
One Customer → Many Orders
```

```java
@OneToMany(mappedBy = "customer")
private List<Order> orders;
```

`mappedBy` means:

> The relationship is owned by the `customer` field on `Order`.

It refers to the **Java field/property**, not the database column.

---

## 17. Owning Side

The owning side controls the relationship mapping / foreign key updates.

```java
class Order {

    @ManyToOne
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
```

Here `Order.customer` is the owning side.

Inverse side:

```java
class Customer {

    @OneToMany(mappedBy = "customer")
    private List<Order> orders;
}
```

---

## 18. Bidirectional Relationships

Example:

```java
class Customer {

    @OneToMany(mappedBy = "customer")
    private List<Order> orders;
}

class Order {

    @ManyToOne
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
```

Keep both sides synchronized in application code.

A helper method is useful:

```java
public void addOrder(Order order) {
    orders.add(order);
    order.setCustomer(this);
}
```

---

## 19. One-to-One

```java
@OneToOne
@JoinColumn(name = "profile_id")
private Profile profile;
```

This commonly maps a foreign-key relationship with uniqueness depending on the schema/mapping.

---

## 20. Many-to-Many

Example:

```text
Students ↔ Courses
```

A join table is normally required:

```text
student_course
---------------------
student_id
course_id
```

Example:

```java
@ManyToMany
@JoinTable(
    name = "student_course",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id")
)
private Set<Course> courses;
```

### Practical design

If the relationship has business attributes:

```text
Student
Course
Enrollment
    enrollmentDate
    grade
    status
```

prefer modeling `Enrollment` as its own entity.

---

# Cascades and Fetching

## 21. Cascade Types

Cascade controls which entity operations propagate to associated entities.

```java
CascadeType.PERSIST
CascadeType.MERGE
CascadeType.REMOVE
CascadeType.REFRESH
CascadeType.DETACH
CascadeType.ALL
```

Example:

```java
@OneToMany(
    mappedBy = "customer",
    cascade = CascadeType.ALL
)
private List<Order> orders;
```

Important:

```text
Cascade → operation propagation
Fetch   → loading strategy
```

They are different concepts.

---

## 22. `orphanRemoval`

```java
@OneToMany(
    mappedBy = "customer",
    orphanRemoval = true
)
private List<Order> orders;
```

Removing a child from the relationship can cause Hibernate to delete that orphaned entity.

Example:

```java
customer.getOrders().remove(order);
```

Potential result:

```sql
DELETE FROM orders WHERE id = ?;
```

Use this carefully because it is deletion behavior.

---

## 23. FetchType

JPA supports:

```java
FetchType.LAZY
FetchType.EAGER
```

### LAZY

Associated data is loaded when needed.

### EAGER

Associated data is expected to be loaded eagerly.

Common JPA defaults:

```text
@ManyToOne → EAGER
@OneToOne  → EAGER

@OneToMany → LAZY
@ManyToMany → LAZY
```

A common practical approach is to prefer LAZY relationships and explicitly fetch what is required for a use case.

---

# N+1 Problem

## 24. What is N+1?

Suppose we query 100 customers:

```java
List<Customer> customers = customerRepository.findAll();
```

One query:

```sql
SELECT * FROM customer;
```

Then:

```java
for (Customer customer : customers) {
    customer.getOrders().size();
}
```

Hibernate may execute:

```text
1 query for customers
+
100 queries for orders
=
101 queries
```

Hence:

```text
N + 1
```

---

## 25. Why N+1 Happens

A useful interview answer:

> N+1 occurs when the application loads N parent records and then causes the associated data to be loaded individually for each parent.

Do not oversimplify it as:

> "LAZY loading causes N+1."

Lazy loading can expose N+1, but the deeper problem is the way the object graph is fetched.

---

## 26. N+1 Example

```java
List<Customer> customers =
    customerRepository.findAll();

for (Customer customer : customers) {
    System.out.println(customer.getOrders());
}
```

Potential SQL:

```sql
SELECT * FROM customer;

SELECT * FROM orders WHERE customer_id = 1;
SELECT * FROM orders WHERE customer_id = 2;
SELECT * FROM orders WHERE customer_id = 3;
...
```

For 100 customers:

```text
101 queries
```

---

## 27. Solve N+1 with JOIN FETCH

JPQL:

```java
@Query("""
    SELECT c
    FROM Customer c
    JOIN FETCH c.orders
""")
List<Customer> findCustomersWithOrders();
```

This tells Hibernate to fetch the association as part of the query.

For parents that may have no children, use:

```java
@Query("""
    SELECT DISTINCT c
    FROM Customer c
    LEFT JOIN FETCH c.orders
""")
List<Customer> findCustomersWithOrders();
```

`DISTINCT` can be needed because one customer may appear in multiple joined rows.

---

## 28. EntityGraph

Another approach:

```java
@EntityGraph(attributePaths = {"orders"})
List<Customer> findAll();
```

This explicitly defines what should be fetched for that repository operation without globally making the relationship EAGER.

---

## 29. Batch Fetching

Hibernate can batch lazy association loading.

```java
@BatchSize(size = 50)
@OneToMany(mappedBy = "customer")
private List<Order> orders;
```

Instead of:

```text
SELECT orders WHERE customer_id = 1
SELECT orders WHERE customer_id = 2
SELECT orders WHERE customer_id = 3
...
```

Hibernate can group IDs:

```sql
SELECT *
FROM orders
WHERE customer_id IN (?, ?, ?, ...);
```

This reduces database round trips.

---

## 30. `@Fetch(FetchMode.SUBSELECT)`

Hibernate-specific option for collection fetching.

Conceptually:

```sql
SELECT *
FROM orders
WHERE customer_id IN (
    SELECT id FROM customer ...
);
```

It is Hibernate-specific, not standard JPA.

---

## 31. N+1 Solution Comparison

| Technique | Main idea |
|---|---|
| JOIN FETCH | Fetch association in the query |
| EntityGraph | Specify fetch graph for the operation |
| Batch fetching | Group lazy-loading queries |
| SUBSELECT | Hibernate-specific collection strategy |
| DTO projection | Fetch only required data |
| Separate queries | Explicitly control each data load |

---

## 32. Multiple Collection Fetches

Be careful when fetching multiple `@OneToMany` collections.

Example:

```text
Customer
 ├── orders
 └── addresses
```

If:

```text
3 orders × 4 addresses
```

are joined together, SQL may produce:

```text
12 rows
```

This can cause:

- Huge result sets
- Duplicate data
- Memory pressure
- Poor performance
- Hibernate `MultipleBagFetchException` in applicable cases

Possible approaches:

- Fetch one collection at a time.
- Batch fetch.
- Use separate queries.
- Use DTO projections.
- Redesign the query/use case.

---

# Lazy Loading

## 33. LazyInitializationException

Common error:

```text
LazyInitializationException:
could not initialize proxy - no Session
```

This commonly occurs when lazy data is accessed after the persistence context/session has closed.

Bad pattern:

```java
Customer customer = service.getCustomer();

// transaction/session already ended

customer.getOrders().size();
```

Better:

```java
@Transactional
public CustomerDto getCustomer(Long id) {
    Customer customer = repository.findCustomerWithOrders(id);
    return CustomerDto.from(customer);
}
```

Fetch required data while the persistence context is active.

### Avoid

Making everything EAGER just to hide the problem.

---

# JPQL / SQL

## 34. JPQL

JPQL works with **entities and Java fields**, not directly with tables and columns.

```sql
SELECT c
FROM Customer c
WHERE c.name = :name
```

Here:

```text
Customer → entity
name     → Java field
```

---

## 35. Native Query

Native SQL works directly with database tables and columns.

```java
@Query(
    value = "SELECT * FROM customers WHERE name = :name",
    nativeQuery = true
)
List<Customer> findByName(String name);
```

Use it when database-specific SQL or features are needed and JPQL is not sufficient.

---

## 36. JPQL vs Native SQL

| JPQL | Native SQL |
|---|---|
| Entity-oriented | Database-oriented |
| More portable | Database-specific |
| Uses entity/field names | Uses table/column names |
| ORM understands object model | Direct SQL |

---

# Transactions

## 37. Transactions

A transaction groups database operations into one atomic unit.

```java
@Transactional
public void transferMoney(...) {
    ...
}
```

Conceptually:

```text
BEGIN
  operation 1
  operation 2
  operation 3
COMMIT
```

On rollback:

```text
BEGIN
  operation 1
  operation 2
  ERROR
ROLLBACK
```

---

## 38. ACID

### Atomicity

All operations succeed or the transaction is rolled back.

### Consistency

Database invariants/rules remain valid.

### Isolation

Concurrent transactions are isolated according to the selected isolation level.

### Durability

Committed data survives failures according to the database's durability guarantees.

---

## 39. Isolation Levels

Common isolation levels:

```text
READ_UNCOMMITTED
READ_COMMITTED
REPEATABLE_READ
SERIALIZABLE
```

Potential anomalies:

```text
Dirty read
Non-repeatable read
Phantom read
```

Exact behavior depends on the database.

---

## 40. Optimistic Locking

Useful when concurrent updates are possible.

```java
@Version
private Long version;
```

Example:

```text
User A reads version 5
User B reads version 5

User A updates → version 6

User B tries to update version 5
→ optimistic locking conflict
```

Hibernate can throw an optimistic locking exception.

---

## 41. Pessimistic Locking

Pessimistic locking asks the database to lock rows.

Example:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Conceptually:

```sql
SELECT ...
FOR UPDATE;
```

Useful when the application needs database-level locking around concurrent modifications.

---

## 42. Optimistic vs Pessimistic Locking

| Optimistic | Pessimistic |
|---|---|
| Assumes conflicts are uncommon | Assumes conflicts may occur |
| Uses version/checking | Uses database locks |
| Good concurrency when conflicts are rare | Can block other transactions |
| Conflict detected during update | Conflict controlled through locking |

---

## 43. Transaction Propagation

Common propagation modes:

```text
REQUIRED
REQUIRES_NEW
SUPPORTS
MANDATORY
NOT_SUPPORTED
NEVER
NESTED
```

### REQUIRED

Use the existing transaction if present; otherwise create one.

### REQUIRES_NEW

Suspends the existing transaction and creates a new transaction.

Conceptually:

```text
Outer transaction
       |
       +-- inner REQUIRES_NEW transaction
```

The inner transaction can commit independently of the outer transaction.

---

## 44. Transaction Rollback Trap

Spring does not simply mean:

> Every exception causes rollback.

By default, Spring commonly rolls back for unchecked exceptions (`RuntimeException`) and errors. Checked exceptions require appropriate configuration if rollback is desired.

Example:

```java
@Transactional(rollbackFor = Exception.class)
```

---

## 45. `@Transactional(readOnly = true)`

For read-only service methods:

```java
@Transactional(readOnly = true)
public CustomerDto getCustomer(Long id) {
    ...
}
```

This communicates intent and can allow optimizations depending on the transaction manager/provider/database.

It is not a universal guarantee that every underlying database operation becomes physically read-only.

---

# Spring Data JPA

## 46. `save()` vs `saveAndFlush()`

```java
repository.save(entity);
```

does not necessarily mean SQL is executed immediately.

```java
repository.saveAndFlush(entity);
```

forces a flush.

Remember:

```text
save
  ↓
persistence operation

flush
  ↓
synchronize SQL

commit
  ↓
complete transaction
```

---

## 47. `findById()` vs `getReferenceById()`

```java
findById(id)
```

normally retrieves the entity and returns an `Optional`.

```java
getReferenceById(id)
```

can return a lazy reference/proxy and defer database access until the entity is accessed.

This can be useful when you only need a reference to another entity.

---

## 48. `find()` vs `getReference()`

JPA:

```java
entityManager.find(User.class, id);
```

loads/finds the entity.

```java
entityManager.getReference(User.class, id);
```

returns a reference/proxy and can defer database access.

# DTOs and Query Design

## 49. DTO Projection

Sometimes you do not need a full entity graph.

JPQL example:

```java
SELECT new com.example.CustomerDto(
    c.id,
    c.name
)
FROM Customer c
```

Benefits:

- Less data loaded
- Less memory
- Fewer unnecessary associations
- Smaller API payloads
- Better control over read models

---

## 50. Entity vs DTO

Entities are primarily persistence/domain objects.

DTOs are designed for data transfer.

Typical flow:

```text
Database
   ↓
Entity
   ↓
Service
   ↓
DTO
   ↓
Controller/API
```

Returning entities directly can cause:

- Lazy-loading queries
- N+1 problems
- Recursive serialization
- Huge response graphs
- Tight coupling between database model and API contract

---

## 51. Why Returning Entities Directly Can Be Risky

Example:

```text
Customer
 └── orders
      └── customer
           └── orders
```

Serialization can cause:

- Infinite recursion
- Huge responses
- Lazy initialization problems
- Unintended SQL queries

DTOs give explicit control over the API contract.

# Other JPA Concepts

## 52. `@MappedSuperclass`

Useful for common entity fields.

```java
@MappedSuperclass
public abstract class BaseEntity {

    @Id
    @GeneratedValue
    protected Long id;

    protected Instant createdAt;
    protected Instant updatedAt;
}
```

Then:

```java
@Entity
public class User extends BaseEntity {
}
```

The base class is not necessarily a standalone entity/table.

---

## 53. `@Embeddable`

Useful for value objects.

```java
@Embeddable
public class Address {
    private String city;
    private String country;
}
```

Then:

```java
@Embedded
private Address address;
```

The fields can be stored in the owning entity's table.

---

## 54. `@ElementCollection`

Useful for collections of basic values/value objects.

```java
@ElementCollection
private List<String> phoneNumbers;
```

JPA stores the collection in a separate collection table.

It is different from a collection of entities.

---

## 55. Inheritance Strategies

JPA supports:

```text
SINGLE_TABLE
JOINED
TABLE_PER_CLASS
```

### SINGLE_TABLE

All classes use one table.

Pros:

- Simple
- Efficient polymorphic queries

Cons:

- Potentially many nullable columns

### JOINED

Base and subclass data are stored in related tables.

Pros:

- More normalized

Cons:

- More joins

### TABLE_PER_CLASS

Concrete classes have their own tables.

Polymorphic queries can be more expensive/complex.

# Performance

## 56. How to Debug N+1

When an endpoint is slow:

1. Enable SQL logging.
2. Inspect the number of SQL statements.
3. Identify repeated queries.
4. Find the relationship being initialized.
5. Check whether the endpoint actually needs the association.
6. Choose an appropriate fetch strategy.
7. Test with realistic data volume.

Look for:

```text
SELECT customers ...

SELECT orders WHERE customer_id = 1
SELECT orders WHERE customer_id = 2
SELECT orders WHERE customer_id = 3
...
```

---

## 57. When NOT to JOIN FETCH

Do not blindly fetch everything.

Problems include:

- Huge result sets
- Duplicate rows
- Multiple collection joins
- Pagination problems
- High memory consumption

If an API only needs:

```text
Customer.id
Customer.name
```

do not automatically fetch:

```text
Customer
 ├── orders
 ├── addresses
 ├── payments
 ├── notifications
 └── auditLogs
```

Fetch the smallest object graph required by the use case.

---

## 58. Pagination + Fetch Join

Collection fetch joins can be problematic with pagination.

Why?

A parent with many children produces many SQL rows.

Example:

```text
Customer 1 → 100 orders
Customer 2 → 2 orders
```

Applying `LIMIT/OFFSET` to the joined rows is not the same as limiting customers.

A common approach:

```text
Step 1:
Page customer IDs

       ↓

Step 2:
Fetch customers + required relationships
for those IDs
```

Other options include:

- Batch fetching
- DTO projections
- Separate optimized queries

---

## 59. Persistence Context and `flush()`

Consider:

```java
@Transactional
public void method() {

    User user = repository.findById(1L).orElseThrow();

    user.setName("A");

    repository.findByName("B");
}
```

Hibernate may flush pending changes before executing certain queries depending on the flush mode and query.

The goal is to keep query results consistent with the current transactional/persistence-context state.

# Interview Scenarios

## 60. Scenario: Find the N+1

Given:

```java
@Entity
class Department {

    @OneToMany(mappedBy = "department")
    private List<Employee> employees;
}
```

```java
List<Department> departments = departmentRepository.findAll();

for (Department department : departments) {
    System.out.println(department.getEmployees().size());
}
```

Reasoning:

1. `findAll()` executes one query.
2. `employees` is lazy.
3. `getEmployees()` initializes each collection.
4. Hibernate may execute one query per department.
5. Total becomes `1 + N`.

Possible solutions:

```text
JOIN FETCH
EntityGraph
Batch fetching
DTO projection
Separate optimized queries
```

---

## 61. Scenario: Why Not Make Everything EAGER?

Suppose:

```text
Customer
 ├── orders
 ├── payments
 ├── addresses
 ├── documents
 └── notifications
```

If everything is EAGER, a simple lookup could trigger substantial unnecessary data loading.

Potential problems:

- More SQL
- More joins
- More memory
- Larger object graphs
- Slower requests
- More difficult query tuning

Better:

> Keep relationships appropriately lazy and explicitly fetch what a particular use case needs.

---

## 62. Scenario: `merge()`

Given:

```java
User detached = ...;

User managed = entityManager.merge(detached);

detached.setName("A");
```

Question:

Will `managed` automatically reflect the later change?

**No.**

`merge()` copied state into the managed instance.

Use:

```java
managed.setName("A");
```

because `managed` is tracked by the persistence context.

---

## 63. Scenario: Dirty Checking

```java
@Transactional
public void update(Long id) {

    User user = repository.findById(id).orElseThrow();

    user.setName("Harsh");
}
```

Question:

Where is `save()`?

Answer:

The entity is managed inside the transaction. Hibernate's dirty checking detects the change and generates an `UPDATE` during flush.

---

## 64. Scenario: LazyInitializationException

Bad:

```java

// transaction already ended

customer.getOrders().size();
```

Better:

```java
@Transactional
public CustomerDto getCustomer(Long id) {
    Customer customer = repository.findCustomerWithOrders(id);

```

Fetch the required association while the persistence context is active.

## 65. Scenario: Pagination

Question:

> Why can a collection `JOIN FETCH` be problematic with pagination?

Because one parent can produce many joined rows.

Example:

```text
Customer 1 → 100 orders
Customer 2 → 2 orders
```

A SQL limit over joined rows does not directly represent a page of customers.

Common strategy:

```text
Query 1:
Get a page of customer IDs

       ↓

Query 2:
Fetch customers + required orders
for those IDs
```

---

## 66. Scenario: Many-to-Many

Question:

> When should you avoid `@ManyToMany`?

When the relationship itself contains business attributes.

Instead of:

```text
Student ↔ Course
```

use:

```text
Student
   |
Enrollment
   |
Course
```

with:

```text
Enrollment
- student
- course
- enrolledAt
- grade
- status
```

# Rapid Interview Questions

## 67. What is JPA?

JPA is a Java specification for persistence and ORM. Hibernate is a common implementation.

## 68. What is Hibernate?

Hibernate is an ORM framework and a JPA provider.

## 69. What is persistence context?

A managed set of entity instances associated with an `EntityManager`, providing identity management, dirty checking, and first-level caching.

## 70. What is dirty checking?

Hibernate detects changes to managed entities and generates SQL during flush.

## 71. What is N+1?

One query loads N parent entities, followed by N additional queries to load related data individually.

## 72. How do you solve N+1?

Depending on the use case:

- `JOIN FETCH`
- EntityGraph
- Batch fetching
- DTO projections
- Separate optimized queries

## 73. Does EAGER solve N+1?

No. EAGER does not guarantee an optimal query strategy.

## 74. What is `mappedBy`?

It identifies the inverse side of a bidirectional relationship and points to the owning-side field/property.

## 75. What is cascade?

It propagates selected entity lifecycle operations to associated entities.

## 76. What is `orphanRemoval`?

It can delete an associated child when it becomes an orphan.

## 77. `persist()` vs `merge()`?

`persist()` makes a new entity managed. `merge()` copies state into a managed instance and returns that instance.

## 78. What is lazy loading?

Associated data is loaded when it is accessed rather than necessarily when the parent is initially loaded.

## 79. What is LazyInitializationException?

It commonly occurs when a lazy association is accessed after the persistence context/session has closed.

## 80. What is optimistic locking?

Concurrency control using version/checking, commonly with `@Version`.

## 81. What is pessimistic locking?

Database-level locking used to control concurrent access.

## 82. What is `@Version`?

A field used by optimistic locking to detect conflicting updates.

## 83. What is flush?

Synchronizing pending persistence-context changes with the database.

## 84. Flush vs commit?

Flush sends/synchronizes changes to the database; commit completes the transaction.

## 85. First-level vs second-level cache?

L1 is persistence-context scoped. L2 can be shared across persistence contexts.

## 86. Why use DTOs?

To control API data, avoid exposing persistence internals, reduce unnecessary loading, and avoid serialization/lazy-loading issues.

# Final Mental Model

When answering JPA/Hibernate questions, think in this order:

```text
1. What Java object am I working with?
              ↓
2. Is it managed by the persistence context?
              ↓
3. What relationship am I accessing?
              ↓
4. Is that relationship LAZY or EAGER?
              ↓
5. What SQL will Hibernate likely generate?
              ↓
6. How many queries will execute?
              ↓
7. Is there an N+1 / Cartesian multiplication issue?
              ↓
8. Can I fetch exactly what I need?
              ↓
9. What happens at flush/commit?
              ↓
10. What happens if another transaction updates it?
```

This mental model is especially useful for JPA performance, debugging, and system-design interview questions.
