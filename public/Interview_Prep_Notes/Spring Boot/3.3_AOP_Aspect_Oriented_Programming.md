# 3.3 AOP — Aspect-Oriented Programming

## 1. What problem does AOP solve?

AOP (Aspect-Oriented Programming) is used to separate **cross-cutting concerns** from normal business logic.

Examples of cross-cutting concerns:

- Logging
- Transactions
- Security / authorization
- Caching
- Metrics
- Auditing
- Distributed tracing

### Without AOP

Suppose several services need logging:

```java
public void createOrder() {

    log.info("createOrder started");

    // business logic

    log.info("createOrder completed");
}
```

Another method may repeat the same code:

```java
public void cancelOrder() {

    log.info("cancelOrder started");

    // business logic

    log.info("cancelOrder completed");
}
```

This causes the same concern to be scattered across many classes.

### With AOP

Business code can remain focused:

```java
@Service
public class OrderService {

    public void createOrder() {
        // only business logic
    }
}
```

A separate aspect handles logging for many methods.

### Interview definition

> AOP is a way of separating cross-cutting concerns such as logging, transactions, security, caching, and metrics from business logic.

---

# 2. Cross-Cutting Concerns

A cross-cutting concern is functionality that affects multiple unrelated parts of an application.

Conceptually:

```text
                    Application
                         |
          +--------------+--------------+
          |              |              |
    OrderService   PaymentService   UserService
          |              |              |
          +--------------+--------------+
                         |
              Cross-cutting concerns
              -----------------------
              Logging
              Security
              Transactions
              Caching
              Metrics
```

Instead of writing:

```text
logging();
securityCheck();
startTransaction();
businessLogic();
commitTransaction();
```

inside every method, AOP allows these concerns to be centralized.

---

# 3. Aspect

An **Aspect** is the component that contains the implementation of a cross-cutting concern.

Example:

```java
@Aspect
@Component
public class LoggingAspect {

}
```

The aspect might say:

> Whenever selected service methods execute, log information about the method.

### Interview definition

> An aspect encapsulates a cross-cutting concern, such as logging, security, transactions, or caching.

---

# 4. Advice

**Advice** defines what code should execute and when it should execute.

Spring AOP provides several common advice types:

- `@Before`
- `@After`
- `@AfterReturning`
- `@AfterThrowing`
- `@Around`

---

## 4.1 `@Before`

Runs before the target method.

```java
@Before("execution(* com.example.service.*.*(..))")
public void beforeMethod() {
    System.out.println("Before method");
}
```

Flow:

```text
Client
  |
  v
@Before
  |
  v
Target Method
```

Example:

```java
public void createOrder() {
    System.out.println("Creating order");
}
```

Output:

```text
Before method
Creating order
```

### Common uses

- Logging
- Authorization checks
- Validation
- Audit preparation

---

# 5. `@After`

Runs after the target method finishes, regardless of whether it returns normally or throws an exception.

```java
@After("execution(* com.example.service.*.*(..))")
public void afterMethod() {
    System.out.println("After method");
}
```

Conceptually, it behaves similarly to a `finally` block.

```text
              Target method
               /         \
          success       exception
              \           /
                   |
                 @After
```

---

# 6. `@AfterReturning`

Runs only when the target method successfully returns.

```java
@AfterReturning(
    pointcut = "execution(* com.example.service.*.*(..))",
    returning = "result"
)
public void afterReturning(Object result) {
    System.out.println("Result = " + result);
}
```

Flow:

```text
Target method
      |
      v
Successful return
      |
      v
@AfterReturning
```

If the target throws an exception:

```text
Target method
      |
      v
Exception
      |
      X
@AfterReturning does not run
```

---

# 7. `@AfterThrowing`

Runs when the target method throws an exception.

```java
@AfterThrowing(
    pointcut = "execution(* com.example.service.*.*(..))",
    throwing = "ex"
)
public void afterThrowing(Exception ex) {
    System.out.println("Exception: " + ex.getMessage());
}
```

Flow:

```text
Target method
      |
      v
Exception
      |
      v
@AfterThrowing
```

### Common uses

- Error logging
- Monitoring failures
- Auditing failed operations

---

# 8. `@Around`

`@Around` surrounds the target method.

It is the most powerful advice type because it can execute code:

- Before the target method
- After the target method
- Instead of the target method
- Conditionally before calling the target

Example:

```java
@Around("execution(* com.example.service.*.*(..))")
public Object aroundMethod(ProceedingJoinPoint pjp)
        throws Throwable {

    System.out.println("Before");

    Object result = pjp.proceed();

    System.out.println("After");

    return result;
}
```

Flow:

```text
Client
  |
  v
@Around
  |
  | before
  v
Target Method
  |
  | after
  v
@Around
  |
  v
Client
```

## What is `proceed()`?

```java
pjp.proceed();
```

means:

> Execute the actual target method.

For example:

```java
Object result = pjp.proceed();
```

means:

```text
Aspect
  |
  v
Execute target method
  |
  v
Get result
```

### Important

An `@Around` advice can choose not to call `proceed()`.

This is useful for caching.

Example concept:

```java
@Around(...)
public Object cache(ProceedingJoinPoint pjp) throws Throwable {

    Object cachedValue = cache.get(...);

    if (cachedValue != null) {
        return cachedValue;
    }

    Object result = pjp.proceed();

    cache.put(..., result);

    return result;
}
```

If the cache contains the value:

```text
Cache hit
   |
   v
Return cached value
   |
   X
Target method never executes
```

---

# 9. Advice Types Summary

| Advice | When it runs |
|---|---|
| `@Before` | Before target method |
| `@After` | After target method regardless of outcome |
| `@AfterReturning` | After successful return |
| `@AfterThrowing` | When target throws an exception |
| `@Around` | Wraps the entire method execution |

Mental model:

```text
                 @Before
                    |
                    v
              Target Method
               /         \
          success       exception
             |              |
             v              v
     @AfterReturning   @AfterThrowing
             \              /
              \            /
                 @After
```

`@Around` can wrap the whole execution.

---

# 10. Join Point

A **join point** is a point during program execution where an aspect can potentially be applied.

In general AOP terminology, join points can include things such as:

- Method execution
- Method call
- Field access
- Constructor execution

However, an important Spring AOP interview point is:

> Spring AOP primarily supports method-execution join points.

For example:

```java
public void createOrder() {
}
```

The execution of:

```java
createOrder()
```

is a join point that Spring AOP can intercept.

---

# 11. Pointcut

A **pointcut** tells Spring:

> Which join points should this aspect apply to?

Example:

```java
execution(* com.example.service.*.*(..))
```

This is a **pointcut expression**.

It selects method executions based on rules such as:

- Return type
- Package
- Class
- Method name
- Arguments

---

# 12. Aspect vs Advice vs Join Point vs Pointcut

This is important for interviews.

```text
Aspect
  |
  +-- Cross-cutting concern

Advice
  |
  +-- What code should execute?

Join Point
  |
  +-- Possible execution/interception point

Pointcut
  |
  +-- Which join points should be selected?

Proxy
  |
  +-- How Spring intercepts the call
```

Easy example:

```java
@Aspect
public class LoggingAspect {

    @Around("execution(* com.example.service.*.*(..))")
    public Object log(ProceedingJoinPoint pjp)
            throws Throwable {

        System.out.println("Before");

        Object result = pjp.proceed();

        System.out.println("After");

        return result;
    }
}
```

Here:

```text
LoggingAspect
    -> Aspect

@Around
    -> Advice

execution(...)
    -> Pointcut expression

Method execution
    -> Join point

Spring proxy
    -> Mechanism used to intercept the call
```

---

# 13. How Spring Implements AOP

Spring AOP is primarily implemented using **runtime proxies**.

Instead of giving the caller a direct reference to the target object:

```text
Client
  |
  v
Target Object
```

Spring can place a proxy in front:

```text
Client
  |
  v
Spring Proxy
  |
  v
Target Object
```

The proxy can run interceptors/advice before delegating to the target.

Conceptually:

```text
Client
  |
  v
Proxy
  |
  +----> @Before
  |
  v
Target Method
  |
  +----> @After
  |
  v
Client
```

This proxy mechanism is the key to understanding Spring AOP.

---

# 14. JDK Dynamic Proxy

Spring can use a **JDK dynamic proxy** when the target is exposed through an interface.

Example:

```java
public interface PaymentService {
    void pay();
}
```

Implementation:

```java
@Service
public class PaymentServiceImpl implements PaymentService {

    @Override
    public void pay() {
        System.out.println("Payment");
    }
}
```

Conceptually:

```text
PaymentService interface
          ^
          |
      JDK Proxy
          |
          v
PaymentServiceImpl
```

The proxy implements the interface.

### Interview statement

> JDK dynamic proxies are interface-based proxies.

---

# 15. CGLIB / Subclass Proxy

If a class doesn't implement an interface, Spring can use subclass-based proxying.

Example:

```java
@Service
public class OrderService {

    public void createOrder() {
        System.out.println("Order");
    }
}
```

Conceptually:

```text
OrderServiceProxy
       extends
OrderService
```

Flow:

```text
Client
  |
  v
OrderServiceProxy
  |
  v
OrderService
```

For interviews, remember:

```text
JDK Dynamic Proxy
    -> Interface-based

CGLIB-style proxy
    -> Subclass-based
```

Modern Spring integrates the subclassing mechanism into Spring's proxy infrastructure, but the interview distinction above remains useful.

---

# 16. JDK Proxy vs CGLIB

| | JDK Dynamic Proxy | CGLIB / Subclass Proxy |
|---|---|---|
| Based on | Interface | Class inheritance |
| Requires interface? | Yes | No |
| Mechanism | Implements interface | Extends target class |
| Can proxy class without interface? | No | Yes |
| Final class | Not applicable in the same way | Cannot subclass final class |
| Final method | Interface dispatch constraints | Cannot override final method |

Interview answer:

> JDK dynamic proxies work through interfaces, while CGLIB-style proxies work through subclassing the target class.

# 17. Self-Invocation Gotcha

This is one of the most important Spring AOP concepts.

Suppose:

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // database operation
    }
}
```

An external caller does:

```java
orderService.createOrder();
```

Conceptually:

```text
Client
  |
  v
Spring Proxy
  |
  v
Target.createOrder()
```

The proxy can apply the advice.

But inside:

```java
createOrder() {
    saveOrder();
}
```

the call is effectively:

```java
this.saveOrder();
```

That means:

```text
Target.createOrder()
       |
       | this.saveOrder()
       v
Target.saveOrder()
```

The second call does not go through the proxy.

Therefore proxy-based advice doesn't get another opportunity to intercept it.

---

# 18. Why Does Self-Invocation Bypass AOP?

External call:

```java
orderService.createOrder();
```

Conceptually:

```text
Client
  |
  v
Proxy
  |
  v
Target.createOrder()
```

AOP can intercept the call.

Internal call:

```java
this.saveOrder();
```

Conceptually:

```text
Target
  |
  v
this.saveOrder()
  |
  v
Target.saveOrder()
```

The proxy is skipped.

Therefore:

```text
No proxy
   |
   v
No proxy interception
   |
   v
Proxy-based advice is bypassed
```

### Interview answer

> Spring AOP works through a proxy. When a method is called from outside the bean, the call goes through the proxy and the advice can execute. But when one method directly calls another method on the same object using `this`, the call stays inside the target object and bypasses the proxy.

---

# 19. Why This Matters for `@Transactional`

Consider:

```java
@Transactional
public void methodA() {
    methodB();
}

@Transactional
public void methodB() {
}
```

If the caller invokes:

```java
service.methodA();
```

then `methodA()` can be intercepted because the external call goes through the proxy.

But:

```text
methodA()
   |
   v
this.methodB()
```

doesn't pass through the proxy.

Therefore don't think:

> "`@Transactional` is attached to the method, so the transaction must always start."

A better mental model is:

> The Spring transaction interceptor runs when the method invocation passes through the Spring proxy.

This is a very important interview concept.

# 20. Building Our Own `@Transactional`

This is a simplified learning example showing how an annotation + aspect can work together.

## Step 1 — Create a custom annotation

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface MyTransactional {
}
```

### `@interface`

```java
public @interface MyTransactional {
}
```

means:

> Define a custom annotation.

### `@Target`

```java
@Target(ElementType.METHOD)
```

means:

> This annotation can be placed on methods.

Example:

```java
@MyTransactional
public void transferMoney() {
}
```

### `@Retention`

```java
@Retention(RetentionPolicy.RUNTIME)
```

means:

> Keep the annotation available at runtime.

This matters because Spring needs to inspect it while the application is running.

---

# 21. Step 2 — Use the Custom Annotation

```java
@Service
public class PaymentService {

    @MyTransactional
    public void transferMoney() {

        System.out.println("Transfer money");

    }
}
```

At this point, nothing automatically starts a transaction.

The annotation is just metadata.

We need an aspect that gives it behavior.

---

# 22. Step 3 — Create the Transaction Aspect

```java
@Aspect
@Component
public class MyTransactionAspect {

    @Around("@annotation(MyTransactional)")
    public Object transaction(
            ProceedingJoinPoint joinPoint) throws Throwable {

        System.out.println("BEGIN TRANSACTION");

        try {

            Object result = joinPoint.proceed();

            System.out.println("COMMIT");

            return result;

        } catch (Exception e) {

            System.out.println("ROLLBACK");

            throw e;
        }
    }
}
```

The flow becomes:

```text
@MyTransactional
       |
       v
@Around("@annotation(MyTransactional)")
       |
       v
Spring Proxy
       |
       v
BEGIN TRANSACTION
       |
       v
Real method
       |
       +---- success ----> COMMIT
       |
       +---- exception --> ROLLBACK
```

This is a **simplified educational version** of transaction interception.

A real transaction implementation needs a transaction manager and has much more behavior, including propagation, isolation, resource handling, and rollback rules.

---

# 23. Understanding `@Around("@annotation(MyTransactional)")`

This expression:

```java
@Around("@annotation(MyTransactional)")
```

means approximately:

> Run this `@Around` advice for methods that have the `@MyTransactional` annotation.

So if you have:

```java
@MyTransactional
public void transferMoney() {
}
```

the aspect applies.

But:

```java
public void getBalance() {
}
```

doesn't have the annotation, so this particular pointcut doesn't select it.

This is often easier to understand than a broad `execution(...)` expression.

---

# 24. Understanding `execution(* com.example.service.*.*(..))`

Now let's understand the expression that originally looked confusing:

```java
@Around("execution(* com.example.service.*.*(..))")
```

The part inside quotes is a **pointcut expression**.

The string is not normal Java syntax.

Java sees:

```java
"execution(* com.example.service.*.*(..))"
```

as a `String`.

Spring/AspectJ's pointcut parser interprets that String as a rule describing which method executions should be intercepted.

Think of it similarly to:

```java
"SELECT * FROM users"
```

being a String that a database interprets as SQL.

Or:

```java
"/users/{id}"
```

being a String interpreted as a web route.

---

# 25. Breaking Down `execution(...)`

Take:

```text
execution(* com.example.service.*.*(..))
```

Break it into:

```text
execution(
    *                       <- return type
    com.example.service     <- package
    *                       <- class
    *                       <- method
    (..)                    <- arguments
)
```

---

# 26. `execution(...)`

```text
execution(...)
```

means:

> Match method execution join points.

Spring AOP primarily works with method execution join points.

---

# 27. First `*` — Return Type

```text
execution(
    *
    ...
)
```

The first `*` means:

> Any return type.

Therefore all of these can match:

```java
String getName()
```

```java
int getAge()
```

```java
User getUser()
```

```java
void deleteUser()
```

because:

```text
* = any return type
```

---

# 28. `com.example.service` — Package

```text
com.example.service
```

means:

> Look in this package.

For example:

```text
com.example.service.OrderService
com.example.service.PaymentService
com.example.service.UserService
```

---

# 29. Second `*` — Class

```text
com.example.service.*
                    ^
```

This `*` means:

> Any class in this package.

So classes such as:

```text
OrderService
PaymentService
UserService
ProductService
```

can match.

---

# 30. Third `*` — Method

```text
com.example.service.*.*
                         ^
```

This `*` means:

> Any method name.

Therefore methods such as:

```java
createOrder()
cancelOrder()
getOrder()
deleteOrder()
```

can match.

---

# 31. `(..)` — Arguments

```text
(..)
```

means:

> Any number of arguments of any types.

Therefore all of these can match:

```java
createOrder()
```

```java
createOrder(100)
```

```java
createOrder(100, "Harsh")
```

```java
createOrder(100, "Harsh", true, 500.0)
```

because:

```text
(..) = any number of arguments
```

---

# 32. Complete Meaning

Therefore:

```java
execution(* com.example.service.*.*(..))
```

roughly means:

> Match execution of any method, with any return type and any arguments, belonging to any class inside `com.example.service`.

Visual representation:

```text
execution(
    *                       <- any return type
    com.example.service     <- package
    *                       <- any class
    *                       <- any method
    (..)                    <- any arguments
)
```

---

# 33. More Specific Pointcuts

Suppose you have:

```text
com.example.service.OrderService
```

with:

```java
public void createOrder() {}

public Order getOrder(int id) {}

public void deleteOrder(String id) {}
```

This:

```java
execution(* com.example.service.*.*(..))
```

matches all three.

---

## Match only `OrderService`

```java
execution(* com.example.service.OrderService.*(..))
```

Meaning:

```text
Any return type
      |
com.example.service
      |
OrderService
      |
Any method
      |
Any arguments
```

---

## Match only `createOrder`

```java
execution(* com.example.service.OrderService.createOrder(..))
```

Now only methods named `createOrder` match.

For example:

```java
createOrder()
createOrder(int id)
createOrder(int id, String user)
```

all match because `(..)` accepts any arguments.

---

## Match a specific argument type

```java
execution(* com.example.service.OrderService.createOrder(int))
```

This specifically matches:

```java
createOrder(int)
```

but not:

```java
createOrder()
```

or:

```java
createOrder(String)
```

# 34. `execution(...)` vs `@annotation(...)`

These are two different ways of selecting methods.

### Select by package/class/method/signature

```java
@Around("execution(* com.example.service.*.*(..))")
```

Meaning:

> Intercept methods based on their location and signature.

### Select by annotation

```java
@Around("@annotation(MyTransactional)")
```

Meaning:

> Intercept methods that have `@MyTransactional`.

For a custom annotation like `@MyTransactional`, the annotation-based pointcut is often easier to understand.

# 36. Important Limitation of This Example

This custom implementation:

```java
System.out.println("BEGIN");
```

does **not** create a real database transaction.

It only demonstrates the AOP mechanism.

A real transaction implementation needs something like:

```text
Transaction Manager
       |
       v
Database Connection
       |
       v
BEGIN
       |
       v
Execute SQL
       |
       +---- success ----> COMMIT
       |
       +---- failure ----> ROLLBACK
```

Spring's actual transaction infrastructure handles this and many additional concerns.

The important interview lesson is:

```text
Custom annotation
        +
Aspect
        +
Pointcut
        +
Proxy
        +
Around advice
        =
Annotation-driven behavior
```

# 37. Real Cross-Cutting Concern Example — Execution Time

A good real-world AOP example is measuring service execution time.

Without AOP:

```java
public void createOrder() {

    long start = System.currentTimeMillis();

    // business logic

    long end = System.currentTimeMillis();

    log.info("Time = " + (end - start));
}
```

You would have to repeat this in many methods.

With AOP:

```java
@Around("execution(* com.example.service.*.*(..))")
public Object measureTime(ProceedingJoinPoint pjp)
        throws Throwable {

    long start = System.currentTimeMillis();

    Object result = pjp.proceed();

    long end = System.currentTimeMillis();

    System.out.println(
        pjp.getSignature()
        + " took "
        + (end - start)
        + " ms"
    );

    return result;
}
```

Now business code stays clean:

```java
@Service
public class OrderService {

    public void createOrder() {
        // only business logic
    }
}
```

### Why AOP is useful here

The execution-time measurement is:

- Not part of the business logic
- Needed across many services
- Repetitive if written manually
- Easy to centralize using an aspect

# 38. Interview Questions and Answers

## Q1. What is AOP?

> AOP is a way of separating cross-cutting concerns such as logging, transactions, security, caching, and metrics from business logic.

---

## Q2. What is an aspect?

> An aspect encapsulates a cross-cutting concern and defines the behavior that should be applied to selected join points.

---

## Q3. What is advice?

> Advice is the code that runs at a selected join point. Spring provides `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing`, and `@Around` advice.

---

## Q4. What is a pointcut?

> A pointcut is a rule that selects which join points should receive an aspect's advice.

---

## Q5. What is a join point in Spring AOP?

> Spring AOP primarily supports method-execution join points. A method execution is a point where Spring can apply proxy-based advice.

---

## Q6. How does Spring implement AOP?

> Spring AOP is primarily proxy-based. Spring creates a runtime proxy around the target bean, and method calls through that proxy can be intercepted by AOP advice.

---

## Q7. JDK proxy vs CGLIB?

> JDK dynamic proxies are interface-based, while CGLIB-style proxies use subclassing and can proxy a class that doesn't implement an interface.

---

## Q8. Why does self-invocation bypass Spring AOP?

> Because an internal call such as `this.methodB()` goes directly from the target object to another method on the same target object. It doesn't go through the Spring proxy, so proxy-based advice isn't triggered for that call.

---

## Q9. What does this mean?

```java
@Around("execution(* com.example.service.*.*(..))")
```

Answer:

> It is a pointcut expression. It matches execution of methods with any return type, in any class under `com.example.service`, with any method name and any number/type of arguments.

# 39. Say This Out Loud in an Interview

### Proxy

> A proxy is an object created by Spring that sits in front of the target bean. Calls through the proxy can be intercepted so Spring can execute AOP advice before, after, or around the target method.

### Self-invocation

> An internal `this.method()` call bypasses the Spring proxy because the call stays inside the target object. Therefore proxy-based AOP advice such as transaction or caching interception may not run for that internal call.

### Cross-cutting concern

> A good example is execution-time monitoring. Instead of scattering timing and logging code throughout every service method, I can use an `@Around` advice to measure method execution centrally.

### `execution(...)`

> `execution(* com.example.service.*.*(..))` is a pointcut expression. The first star means any return type, the package specifies where to look, the next star means any class, the next star means any method, and `(..)` means any arguments.

## One-line interview summary

> **Spring AOP is primarily proxy-based: external method calls go through the proxy and can be intercepted, while internal `this.method()` calls bypass the proxy, which is why self-invocation can bypass proxy-based behavior such as `@Transactional` and caching.**
