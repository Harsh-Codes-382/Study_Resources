# Spring Boot --- Web / MVC / REST Layer Interview Notes

> Interview-focused notes covering Spring MVC request flow, controller
> mappings, filters, interceptors, exception handling, validation, HTTP
> status codes, DTOs, pagination, idempotency, and REST vs RPC.

------------------------------------------------------------------------

# 1. Spring MVC Request Flow

## High-level flow

``` text
HTTP Request
    |
    v
Tomcat / Servlet Container
    |
    v
Servlet Filter Chain
    |
    v
DispatcherServlet
    |
    v
HandlerMapping
    |
    v
HandlerExecutionChain
    |
    v
Interceptor.preHandle()
    |
    v
HandlerAdapter
    |
    v
Controller
    |
    v
Service
    |
    v
Repository
    |
    v
Database
    |
    v
Controller return value
    |
    v
HandlerMethodReturnValueHandler
    |
    v
HttpMessageConverter
    |
    v
Jackson
    |
    v
JSON HTTP Response
```

## Interview answer

> A request first reaches the embedded servlet container such as Tomcat.
> Servlet filters execute before the request reaches Spring MVC. The
> request then reaches Spring's `DispatcherServlet`, which acts as the
> front controller. `DispatcherServlet` uses `HandlerMapping` to find
> the controller handler and a `HandlerAdapter` to invoke it. Spring
> resolves controller arguments such as `@PathVariable`,
> `@RequestParam`, and `@RequestBody`. The controller usually delegates
> to a service and repository. Its return value is then processed and,
> for a REST controller, serialized by an `HttpMessageConverter`,
> typically using Jackson, into JSON.

------------------------------------------------------------------------

# 2. DispatcherServlet

`DispatcherServlet` is the **front controller of Spring MVC**.

Its responsibility is to coordinate request processing.

Conceptually, its main work looks like:

``` text
Request
  |
  v
DispatcherServlet
  |
  +--> Find handler
  |
  +--> Run interceptors
  |
  +--> Invoke controller
  |
  +--> Process return value
  |
  +--> Handle exceptions
  |
  v
Response
```

Internally, the central request-dispatching method is commonly
associated with:

``` java
doDispatch(request, response)
```

You don't need to memorize the source code, but understand the major
stages.

------------------------------------------------------------------------

# 3. HandlerMapping

After `DispatcherServlet` receives the request, Spring needs to
determine:

> Which controller method should handle this request?

That's the job of `HandlerMapping`.

Example:

``` java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public UserResponse getUser(@PathVariable Long id) {
        return userService.getUser(id);
    }
}
```

Request:

``` http
GET /api/users/123
```

Spring conceptually resolves:

``` text
GET /api/users/{id}
        |
        v
UserController.getUser()
```

HandlerMapping can consider more than just the URL:

-   HTTP method
-   path
-   headers
-   `consumes`
-   `produces`
-   request parameters

------------------------------------------------------------------------

# 4. HandlerExecutionChain

HandlerMapping does not simply return a controller method.

Conceptually, it returns a `HandlerExecutionChain` containing:

``` text
HandlerExecutionChain
    |
    +-- Handler
    |
    +-- Interceptors
```

Example:

``` text
Handler:
    UserController.getUser()

Interceptors:
    LoggingInterceptor
    AuthInterceptor
```

This is how Spring knows which interceptors participate in the request.

------------------------------------------------------------------------

# 5. HandlerAdapter

Once Spring knows the handler, it needs a mechanism to invoke it.

That's the job of `HandlerAdapter`.

For annotation-based controllers, Spring commonly uses:

``` text
RequestMappingHandlerAdapter
```

Conceptually:

``` text
DispatcherServlet
      |
      v
HandlerMapping
      |
      v
Controller method
      |
      v
RequestMappingHandlerAdapter
      |
      v
invoke controller
```

### Interview answer

> `HandlerMapping` determines which handler should process the request,
> while `HandlerAdapter` knows how to invoke that handler.

# 6. HandlerMethodArgumentResolver

Controller methods often have parameters such as:

``` java
@GetMapping("/{id}")

        @PathVariable Long id,
        @RequestParam String type,
        @RequestHeader("Authorization") String auth
) {
    ...
}
```

Spring needs to construct those arguments before calling the method.

This is handled through the **HandlerMethodArgumentResolver**
infrastructure.

Think:

``` text
HTTP Request
    |
    v
Argument Resolver
    |
    +--> @PathVariable
    +--> @RequestParam
    +--> @RequestHeader
    +--> @RequestBody
    |
    v
Java method arguments
```

# 9. @RequestBody

Used to deserialize the HTTP request body into a Java object.

Request:

``` http
POST /users
Content-Type: application/json
```

``` json
{
  "name": "John",
  "email": "john@example.com"
}
```

Controller:

``` java
@PostMapping("/users")
public UserResponse createUser(
        @RequestBody CreateUserRequest request
) {
    ...
}
```

Conceptually:

``` text
JSON
  |
  v
HttpMessageConverter
  |
  v
Jackson
  |
  v
CreateUserRequest
```

This is not manually calling Jackson in normal application code. Spring
performs the conversion.

# 10. HttpMessageConverter

`HttpMessageConverter` converts between HTTP data and Java objects.

For JSON:

``` text
Request:

JSON
  |
  v
HttpMessageConverter
  |
  v
Java object
```

For the response:

``` text
Java object
  |
  v
HttpMessageConverter
  |
  v
JSON
```

Spring Boot commonly uses Jackson for JSON.

A common converter is:

``` text
MappingJackson2HttpMessageConverter
```

Conceptually similar to:

``` java
objectMapper.readValue(...)
```

for deserialization and:

``` java
objectMapper.writeValue(...)
```

for serialization.

# 11. Content-Type, consumes, produces

Example:

``` java
@PostMapping(
    value = "/users",
    consumes = "application/json",
    produces = "application/json"
)
public UserResponse createUser(
        @RequestBody CreateUserRequest request
) {
    ...
}
```

Meaning:

``` text
consumes = what request body format is accepted
produces = what response format is produced
```

Important HTTP errors:

``` text
415 Unsupported Media Type
    -> request Content-Type isn't supported

406 Not Acceptable
    -> requested response representation isn't supported
```

# 12. @Controller vs @RestController

## @Controller

Usually used for MVC views.

``` java
@Controller
public class UserController {

    @GetMapping("/users")
    public String users() {
        return "users";
    }
}
```

The return value can represent a view name.

Conceptually:

``` text
Controller
   |
   v
"users"
   |
   v
ViewResolver
   |
   v
HTML
```

## @Controller + @ResponseBody

``` java
@Controller
public class UserController {

    @GetMapping("/users")
    @ResponseBody
    public UserResponse users() {
        return response;
    }
}
```

Now the return value becomes the HTTP response body.

## @RestController

``` java
@RestController
public class UserController {

    @GetMapping("/users")
    public UserResponse users() {
        return response;
    }
}
```

`@RestController` is effectively:

``` text
@Controller
+
@ResponseBody
```

### Interview answer

> `@Controller` is commonly used for Spring MVC controllers that can
> return views, while `@RestController` combines `@Controller` and
> `@ResponseBody`, so method return values are written directly to the
> HTTP response body.

# 14. Filter vs Interceptor

## The one-line distinction

> **Filter = Servlet/HTTP layer. Interceptor = Spring MVC/controller
> layer.**

The request flow:

``` text
HTTP Request
     |
     v
+-------------+
|   FILTER    |  <-- Servlet layer
+-------------+
     |
     v
+------------------+
| DispatcherServlet|
+------------------+
     |
     v
+-------------+
| INTERCEPTOR |  <-- Spring MVC layer
+-------------+
     |
     v
+-------------+
| CONTROLLER  |
+-------------+
```

------------------------------------------------------------------------

# 15. Filter

A Filter belongs to the Servlet API.

Example:

``` java
@Component
public class LoggingFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain
    ) throws IOException, ServletException {

        System.out.println("Before request");

        chain.doFilter(request, response);

        System.out.println("After request");
    }
}
```

The important line:

``` java
chain.doFilter(request, response);
```

means:

> Continue processing the request.

If the filter doesn't call it, downstream processing can stop.

------------------------------------------------------------------------

# 16. What does a Filter know?

A Filter fundamentally works with Servlet concepts:

``` java
ServletRequest
ServletResponse
FilterChain
```

It sees things such as:

-   HTTP method
-   URI
-   headers
-   request/response
-   body handling

But it doesn't inherently know which Spring MVC controller method will
handle the request.

For example, it sees:

``` text
GET /api/users/123
```

but it does not inherently start with:

``` text
UserController.getUser(123)
```

Spring MVC determines that later.

------------------------------------------------------------------------

# 17. When to use a Filter

Use a Filter for concerns at the Servlet/HTTP level.

Typical examples:

-   request/response logging
-   correlation IDs
-   CORS
-   request/response wrapping
-   low-level request processing
-   security infrastructure

Spring Security's web security is primarily filter-based.

Conceptually:

``` text
Request
   |
   v
Spring Security Filter Chain
   |
   v
DispatcherServlet
   |
   v
Controller
```

------------------------------------------------------------------------

# 18. Interceptor

An Interceptor belongs to Spring MVC.

It implements:

``` java
HandlerInterceptor
```

Example:

``` java
@Component
public class LoggingInterceptor
        implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {

        System.out.println("Before controller");

        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex) {

        System.out.println("After controller");
    }
}
```

The interceptor is invoked after Spring MVC has identified the handler.

So it can work with controller/handler information.

------------------------------------------------------------------------

# 19. Interceptor Lifecycle

Simplified successful request:

``` text
preHandle()
    |
    v
Controller
    |
    v
postHandle()
    |
    v
Response processing
    |
    v
afterCompletion()
```

### preHandle()

Runs before controller execution.

``` java
boolean preHandle(...)
```

Returning:

``` java
true
```

allows processing to continue.

Returning:

``` java
false
```

stops the normal handler execution.

### postHandle()

Runs after controller execution but before response processing is fully
completed.

Do not describe it as "the response has definitely reached the client."

### afterCompletion()

Runs after request processing completes, including after exception
handling.

Useful for cleanup/logging.

------------------------------------------------------------------------

# 20. How to Attach an Interceptor to Endpoints

This is important in real Spring applications.

Creating:

``` java
@Component
public class LoggingInterceptor
        implements HandlerInterceptor {
}
```

does NOT automatically make Spring MVC use it.

You must register it.

Create:

``` java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final LoggingInterceptor loggingInterceptor;

    public WebMvcConfig(LoggingInterceptor loggingInterceptor) {
        this.loggingInterceptor = loggingInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {

        registry.addInterceptor(loggingInterceptor)
                .addPathPatterns("/api/users/**");
    }
}
```

Now the interceptor applies to:

``` text
/api/users/123
/api/users
/api/users/anything
```

but not:

``` text
/api/orders/123
```

------------------------------------------------------------------------

# 21. Excluding Endpoints

You can include a broad pattern and exclude specific paths:

``` java
@Override
public void addInterceptors(InterceptorRegistry registry) {

    registry.addInterceptor(loggingInterceptor)
            .addPathPatterns("/api/**")
            .excludePathPatterns(
                    "/api/auth/login",
                    "/api/auth/register"
            );
}
```

Result:

``` text
/api/users/123
    -> interceptor

/api/orders/123
    -> interceptor

/api/auth/login
    -> excluded

/api/auth/register
    -> excluded
```

Important:

``` text
@Component
    |
    v
Spring creates/manages the interceptor bean

addInterceptors(...)
    |
    v
Spring MVC registers it as an MVC interceptor
```

------------------------------------------------------------------------

# 22. Can an Interceptor Be Attached to Exactly One Endpoint?

Yes.

For example:

``` java
registry.addInterceptor(loggingInterceptor)
        .addPathPatterns("/api/users/{id}");
```

However, path patterns are URL-pattern based.

If both methods use the same path:

``` java
@GetMapping("/api/users/{id}")
```

and:

``` java
@DeleteMapping("/api/users/{id}")
```

the same URL pattern can match both.

If behavior must differ by HTTP method, inspect:

``` java
request.getMethod()
```

inside the interceptor or use more appropriate handler-specific logic.

# 24. Simple Analogy

Think of a building.

### Filter = Security guard at the building entrance

Everyone entering the building passes the guard.

The guard doesn't care which desk you're visiting.

``` text
Building entrance
       |
       v
Security Guard
       |
       v
Building
```

### Interceptor = Department receptionist

After the system knows you're going to Engineering, the receptionist can
apply rules for that department.

``` text
Building
   |
   v
Engineering
   |
   v
Receptionist
   |
   v
Engineer
```

Therefore:

``` text
Filter
  = Servlet-level

Interceptor
  = Spring MVC-level
```

# 25. When Should You Choose Which?

## Use Filter when:

Your concern is:

``` text
HTTP request/response
Servlet lifecycle
before Spring MVC
request wrapping
security infrastructure
CORS
correlation ID
```

## Use Interceptor when:

Your concern is:

``` text
Spring MVC
controller execution
handler method
controller-specific logging
handler metadata
MVC-specific checks
```

### Important

Don't think:

``` text
Filter > Interceptor
```

or:

``` text
Interceptor > Filter
```

They solve problems at different layers.

# 26. Global Exception Handling

Instead of writing:

``` java
try {
    ...
} catch (UserNotFoundException e) {
    ...
}
```

inside every controller, use centralized exception handling.

Example:

``` java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleUserNotFound(
            UserNotFoundException ex
    ) {

        ErrorResponse error = new ErrorResponse(
                "USER_NOT_FOUND",
                ex.getMessage()
        );

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(error);
    }
}
```

Now:

``` java
throw new UserNotFoundException(id);
```

can be converted into a consistent HTTP response.

# 31. HTTP Status Codes

  Status   Meaning                 Typical use
  -------- ----------------------- --------------------------------------------
  200      OK                      Successful GET/update
  201      Created                 Successful resource creation
  204      No Content              Successful operation with no response body
  400      Bad Request             Invalid/malformed request or validation
  401      Unauthorized            Authentication missing/failed
  403      Forbidden               Authenticated but insufficient permissions

# 32. 401 vs 403

### 401

Authentication isn't successfully established.

Think:

``` text
Who are you?
```

Examples:

-   missing credentials
-   invalid token
-   expired authentication

### 403

The user is authenticated but doesn't have permission.

Think:

``` text
I know who you are,
but you're not allowed to do this.
```

Example:

``` text
Authenticated user
Role = USER
Required = ADMIN
```

------------------------------------------------------------------------

# 33. 404 vs 409

### 404

Resource doesn't exist.

``` http
GET /users/999999
```

If it doesn't exist:

``` http
404 Not Found
```

### 409

Request conflicts with the current state.

Example:

``` http
POST /users
```

``` json
{
  "email": "existing@example.com"
}
```

If email must be unique:

``` http
409 Conflict
```

# 34. DTO vs Entity

Avoid exposing JPA entities directly from REST APIs.

Bad:

``` java
@GetMapping("/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id).orElseThrow();
}
```

Prefer:

``` java
@GetMapping("/{id}")
public UserResponse getUser(@PathVariable Long id) {

    User user = userService.getUser(id);

    return userMapper.toResponse(user);
}
```

Think:

``` text
Database
   |
   v
Entity
   |
   v
Service
   |
   v
DTO
   |
   v
Controller
   |
   v
JSON
```

For incoming data:

``` text
JSON
   |
   v
Request DTO
   |
   v
Validation
   |
   v
Service
   |
   v
Entity
   |
   v
Database
```

------------------------------------------------------------------------

# 35. Why Exposing Entities Is Dangerous

## 1. Sensitive data leakage

Entity:

``` java
@Entity
public class User {

    private Long id;
    private String name;
    private String email;
    private String passwordHash;
    private boolean admin;
}
```

Returning it directly may expose:

``` json
{
  "id": 1,
  "name": "John",
  "email": "john@example.com",
  "passwordHash": "...",
  "admin": true
}
```

Bad API boundary.

------------------------------------------------------------------------

## 2. Over-posting / Mass Assignment

If you accept the entity directly:

``` java
@PostMapping
public User create(@RequestBody User user) {
    ...
}
```

A client could potentially send fields it should never control:

``` json
{
  "name": "John",
  "admin": true
}
```

A request DTO limits the accepted input:

``` java
public record CreateUserRequest(
        String name,
        String email
) {}
```

------------------------------------------------------------------------

## 3. Persistence/API coupling

Database changes shouldn't automatically become API changes.

If you add:

``` text
internalDatabaseField
```

to your entity, you don't necessarily want that field appearing in the
API.

DTOs provide an explicit API contract.

------------------------------------------------------------------------

## 4. Lazy-loading problems

Example:

``` java
@OneToMany(fetch = FetchType.LAZY)
private List<Order> orders;
```

Returning entities directly can cause:

-   lazy loading during serialization
-   `LazyInitializationException`
-   accidental database queries
-   huge object graphs
-   circular references
-   serialization performance issues

DTOs give you control over exactly what is returned.

------------------------------------------------------------------------

# 36. Pagination

Don't return millions of rows:

``` http
GET /users
```

Instead:

``` http
GET /users?page=0&size=20
```

Spring Data example:

``` java
Page<User> users =
        userRepository.findAll(
                PageRequest.of(page, size)
        );
```

Map entities to DTOs:

``` java
Page<UserResponse> response =
        users.map(userMapper::toResponse);
```

------------------------------------------------------------------------

# 37. Pagination Edge Cases

Don't blindly allow:

``` text
size = 1,000,000
```

Set a maximum, for example:

``` text
size <= 100
```

Also consider large offsets.

This:

``` http
?page=100000
```

can become expensive depending on the database/query.

For large datasets, **cursor/keyset pagination** can be preferable.

Example:

``` http
GET /users?limit=20&after=123
```

Conceptually:

``` sql
SELECT *
FROM users
WHERE id > 123
ORDER BY id
LIMIT 20;
```

This can avoid increasingly expensive offsets.

------------------------------------------------------------------------

# 38. Idempotency

An operation is idempotent when performing it multiple times has the
same intended effect as performing it once.

Common HTTP semantics:

``` text
GET     -> idempotent
PUT     -> idempotent
DELETE  -> generally idempotent
POST    -> generally NOT idempotent
```

Example:

``` http
PUT /users/123
```

``` json
{
  "name": "John"
}
```

Sending it repeatedly results in the same intended state:

``` text
name = John
```

------------------------------------------------------------------------

# 39. POST and Idempotency Keys

Payments are a classic example.

Request:

``` http
POST /payments
Idempotency-Key: abc123
```

Without idempotency:

``` text
Client
  |
  | payment request
  v
Server
  |
  v
Payment created
  |
  X response lost
  |
  v
Client retries
  |
  v
Second payment created
```

With an idempotency key:

``` text
abc123
   |
   v
Already processed?
   |
   +-- YES --> return previous result
   |
   +-- NO ---> process + store result
```

This is especially important for payment/order APIs where retries can
otherwise duplicate side effects.

# 40. REST vs RPC

REST generally models resources:

``` http
GET    /users/123
POST   /users
PUT    /users/123
DELETE /users/123
```

RPC-style APIs model actions:

``` http
POST /createUser
POST /sendEmail
POST /approveOrder
POST /calculatePrice
```

Neither style is automatically correct for every system.

# 42. Exception Flow

If the service throws:

``` java
throw new UserNotFoundException(id);
```

the flow changes:

``` text
Controller / Service
       |
       v
Exception
       |
       v
Spring MVC exception handling
       |
       v
@ControllerAdvice / @RestControllerAdvice
       |
       v
@ExceptionHandler
       |
       v
ErrorResponse / ProblemDetail
       |
       v
HTTP Response
```

Example:

``` java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ProblemDetail> handle(
            UserNotFoundException ex
    ) {

        ProblemDetail problem =
                ProblemDetail.forStatus(404);

        problem.setTitle("User not found");
        problem.setDetail(ex.getMessage());

        return ResponseEntity
                .status(404)
                .body(problem);
    }
}
```

# 45. Short Interview Script

If asked to explain a REST request end-to-end:

> The request first enters the Servlet container and passes through the
> Servlet filter chain. It then reaches `DispatcherServlet`, which is
> Spring MVC's front controller. `DispatcherServlet` uses
> `HandlerMapping` to find the appropriate controller handler and
> obtains a handler execution chain containing applicable interceptors.
> Interceptors can execute before the controller. A `HandlerAdapter`,
> typically `RequestMappingHandlerAdapter` for annotation-based
> controllers, then invokes the controller.
>
> Before invocation, Spring resolves parameters such as `@PathVariable`,
> `@RequestParam`, and `@RequestBody`. For a request body, an
> `HttpMessageConverter`, typically backed by Jackson, deserializes JSON
> into the request DTO. If `@Valid` is present, validation occurs before
> the controller proceeds.
>
> The controller normally delegates to the service layer and returns a
> DTO. Spring's return-value handling infrastructure then uses an
> `HttpMessageConverter` to serialize the DTO into JSON. If an exception
> occurs, Spring's exception handling infrastructure can route it to
> `@RestControllerAdvice` and an appropriate `@ExceptionHandler`, which
> produces the final error response.
