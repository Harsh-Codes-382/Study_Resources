# 2. What `@SpringBootApplication` Actually Does

This is one of the most important Spring Boot interview questions.

When you write:

``` java
@SpringBootApplication
public class Application {
}
```

think of it approximately as:

``` java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
```

So:

``` text
@SpringBootApplication
        │
        ├── @SpringBootConfiguration
        │
        ├── @EnableAutoConfiguration
        │
        └── @ComponentScan
```

## 2.1 `@SpringBootConfiguration`

Marks the class as a Spring Boot configuration class.

Conceptually:

``` text
@SpringBootConfiguration
        ↓
@Configuration
        ↓
Spring configuration class
```

It tells Spring that this class can provide configuration for the
application.

There is normally one main `@SpringBootConfiguration` class in a Spring
Boot application.

------------------------------------------------------------------------

# 3. `@ComponentScan`

`@ComponentScan` tells Spring to search for Spring-managed components.

For example:

``` text
com.example
│
├── Application.java
│
├── controller
│   └── UserController.java
│
├── service
│   └── UserService.java
│
├── repository
│   └── UserRepository.java
│
└── config
    └── SecurityConfig.java
```

If the main class is:

``` java
package com.example;
```

Spring Boot's default component scanning starts from:

``` text
com.example
```

and scans its subpackages.

It can discover:

``` java
@Component
@Service
@Repository
@Controller
@RestController
@Configuration
```

and other component types.

### Important distinction

Do not say:

> `@ComponentScan` creates all the beans.

More accurately:

> `@ComponentScan` discovers component classes and registers bean
> definitions. Bean instances are created later during
> application-context initialization, subject to scope, lazy
> initialization, conditions, etc.

------------------------------------------------------------------------

# 4. Why the Main Class Is Usually at the Root Package

A common project structure is:

``` text
com.company.app
│
├── Application.java
├── controller
├── service
├── repository
└── config
```

The main class is intentionally placed at the root.

Why?

Because default component scanning starts from the package containing
the configuration class.

If you put:

``` text
com.company.app.config.Application
```

then scanning may start around:

``` text
com.company.app.config
```

and your components under:

``` text
com.company.app.service
com.company.app.controller
```

may not be discovered.

This is a common cause of:

``` text
NoSuchBeanDefinitionException
```

or missing-controller/missing-service problems.

------------------------------------------------------------------------

# 5. `@EnableAutoConfiguration`

This is the major Spring Boot feature.

It tells Spring Boot:

> Automatically configure application infrastructure based on the
> dependencies present, the environment, and the conditions defined by
> the auto-configuration classes.

For example, if your application includes:

``` xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

Spring Boot sees the relevant web classes on the classpath and can
configure web infrastructure automatically.

Conceptually:

``` text
spring-boot-starter-web
          │
          ▼
Relevant Spring MVC / Servlet classes available
          │
          ▼
@EnableAutoConfiguration
          │
          ▼
Relevant auto-configurations activated
          │
          ▼
DispatcherServlet
Embedded server
MVC infrastructure
Jackson
etc.
```

You do not have to manually configure all of this.

------------------------------------------------------------------------

# 6. What Is Auto-Configuration?

Spring Boot contains many auto-configuration classes.

Examples include:

``` text
DataSourceAutoConfiguration
WebMvcAutoConfiguration
JacksonAutoConfiguration
TransactionAutoConfiguration
HibernateJpaAutoConfiguration
SecurityAutoConfiguration
```

They use conditions to decide whether they should apply.

For example, conceptually:

``` java
@Configuration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
public class DataSourceAutoConfiguration {
}
```

This roughly means:

``` text
Is DataSource available?
       │
       ├── NO ──> Do not configure this
       │
       └── YES
            │
            ▼
       Is a DataSource
       bean already present?
            │
       ┌────┴─────┐
       ▼          ▼
      YES         NO
       │           │
       │           ▼
       │      Create default
       │      DataSource
       │
       └──> Back off
```

This "back off if the application has provided its own configuration"
behavior is a major part of Spring Boot's design.

------------------------------------------------------------------------

# 7. Important Conditional Annotations

## `@ConditionalOnClass`

``` java
@ConditionalOnClass(RedisTemplate.class)
```

Meaning:

> Apply this configuration if the specified class is available on the
> classpath.

Example:

``` text
Redis dependency present?
       │
       ├── YES → Redis auto-configuration may activate
       └── NO  → It does not
```

------------------------------------------------------------------------

## `@ConditionalOnMissingBean`

``` java
@ConditionalOnMissingBean(DataSource.class)
```

Meaning:

> Create/configure this bean only if an application-provided bean of
> that type is not already present.

This lets developers override Boot's defaults.

------------------------------------------------------------------------

## `@ConditionalOnBean`

``` java
@ConditionalOnBean(MyService.class)
```

Meaning:

> Activate this configuration only when the specified bean exists.

------------------------------------------------------------------------

## `@ConditionalOnProperty`

``` java
@ConditionalOnProperty(
    name = "feature.enabled",
    havingValue = "true"
)
```

Meaning:

> Activate this configuration only when the property has the required
> value.

For example:

``` yaml
feature:
  enabled: true
```

# 8. What Happens When `SpringApplication.run()` Executes?

You write:

``` java
SpringApplication.run(Application.class, args);
```

Conceptually, the startup process is:

``` text
SpringApplication.run()
        │
        ├── Create/configure SpringApplication
        │
        ├── Determine application type
        │
        ├── Prepare Environment
        │
        ├── Create ApplicationContext
        │
        ├── Prepare ApplicationContext
        │
        ├── Load configuration
        │
        ├── Refresh ApplicationContext
        │
        ├── Start web server (web apps)
        │
        ├── Publish startup events
        │
        └── Return ApplicationContext
```

Now let's examine these steps.

# 9. Step 1 --- Determine the Application Type

Spring Boot determines what kind of application is being started.

There are three important conceptual application types:

## 9.1 Servlet Web Application

A traditional HTTP web application using the Servlet stack, usually
Spring MVC.

Typical dependency:

``` text
spring-boot-starter-web
```

Typical server:

``` text
Tomcat
Jetty
Undertow
```

Request flow:

``` text
HTTP Request
     ↓
Servlet Container
     ↓
DispatcherServlet
     ↓
Spring MVC
     ↓
Controller
```

Typical use:

``` java
@RestController
@GetMapping("/users")
```

Think:

> **Blocking/traditional request-response web application built on the
> Servlet API.**

------------------------------------------------------------------------

## 9.2 Reactive Web Application

A non-blocking/reactive HTTP application, typically using Spring
WebFlux.

Typical dependency:

``` text
spring-boot-starter-webflux
```

Typical server/runtime:

``` text
Reactor Netty
```

Request flow:

``` text
HTTP Request
     ↓
Reactive Runtime
     ↓
WebFlux
     ↓
Reactive Controller
     ↓
Mono / Flux
```

Example:

``` java
@GetMapping("/users")
public Flux<User> getUsers() {
    return userService.getUsers();
}
```

Think:

> **Non-blocking/reactive web application designed around
> asynchronous/reactive streams such as `Mono` and `Flux`.**

Important:

Reactive does not simply mean "faster". It is primarily about a
non-blocking programming/execution model and handling I/O efficiently
under concurrency.

------------------------------------------------------------------------

## 9.3 Non-Web Application

An application that does not start an HTTP web server.

Examples:

``` text
Kafka consumer
Batch processor
CLI application
Background worker
Scheduled processing application
```

For example:

``` text
Application
    ↓
Spring ApplicationContext
    ↓
Kafka Consumer
```

No:

``` text
Tomcat
Jetty
Netty HTTP server
```

is required.

Think:

> **A Spring application that uses the Spring container but does not
> expose an HTTP web server.**

You can explicitly configure:

``` java
SpringApplication app = new SpringApplication(Application.class);
app.setWebApplicationType(WebApplicationType.NONE);
app.run(args);
```

------------------------------------------------------------------------

# 10. Application Type Summary

  Type         Typical stack            HTTP server? Common use
  ------------ ---------------------- -------------- --------------------------------------
  `SERVLET`    Spring MVC / Servlet              Yes REST APIs, web applications
  `REACTIVE`   Spring WebFlux                    Yes Non-blocking/reactive APIs
  `NONE`       Core Spring                        No Workers, Kafka consumers, CLI, batch

Interview answer:

> Spring Boot determines whether the application is Servlet-based,
> Reactive, or Non-Web and creates an appropriate `ApplicationContext`.

# 13. Configuration Precedence

Spring Boot supports multiple configuration sources.

For example:

``` text
application.yml
       ↓
Environment variables
       ↓
Command-line arguments
```

Higher-priority property sources can override lower-priority values.

Example:

``` bash
java -jar app.jar --server.port=9090
```

This allows deployment systems to change configuration without modifying
the packaged JAR.

This is especially useful with:

``` text
Docker
Kubernetes
CI/CD
Cloud deployments
```

# 14. Step 3 --- Create the `ApplicationContext`

Spring Boot creates an appropriate `ApplicationContext`.

For a normal MVC application, this is a web-aware application context
based on the Servlet stack.

The `ApplicationContext` is the central Spring container.

It manages things such as:

``` text
Beans
Dependencies
Configuration
Bean lifecycle
Events
Environment
Resources
Infrastructure
```

Conceptually:

``` text
ApplicationContext
       │
       ├── UserController
       ├── UserService
       ├── UserRepository
       ├── DataSource
       ├── EntityManagerFactory
       ├── TransactionManager
       ├── ObjectMapper
       ├── DispatcherServlet
       └── ...
```

# 15. `BeanFactory` vs `ApplicationContext`

A useful interview distinction:

``` text
ApplicationContext
       │
       └── builds on / extends BeanFactory capabilities
```

`BeanFactory` is the core IoC container abstraction.

`ApplicationContext` adds higher-level features such as:

``` text
Application events
Message resolution
Resource loading
Integration with environment
More enterprise-oriented infrastructure
```

In normal Spring Boot applications, you work with `ApplicationContext`.

# 17. Bean Definitions

A `BeanDefinition` is metadata describing how Spring should manage a
bean.

Conceptually:

``` text
BeanDefinition
    │
    ├── Bean class
    ├── Bean name
    ├── Scope
    ├── Dependencies
    ├── Lazy/eager information
    ├── Initialization information
    └── Destruction information
```

For:

``` java
@Service
public class UserService {
}
```

Spring can create bean metadata roughly equivalent to:

``` text
Bean name: userService
Class: UserService
Scope: singleton
Dependencies: ...
```

Important:

> Registering a bean definition and creating the actual bean object are
> separate steps.

# 18. Step 5 --- Bean Creation

Suppose:

``` java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

Spring sees:

``` text
UserService
     │
     └── requires UserRepository
```

It resolves the dependency and creates the object.

Conceptually:

``` text
Create UserService
       │
       ▼
Need UserRepository
       │
       ▼
Find/create UserRepository
       │
       ▼
Inject repository
       │
       ▼
UserService ready
```

This is Dependency Injection.

------------------------------------------------------------------------

# 19. Constructor Injection

Recommended production style:

``` java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

If there is only one constructor, Spring can use it without:

``` java
@Autowired
```

Constructor injection is generally preferred because:

``` text
Dependencies are explicit
Fields can be final
Object cannot normally exist without required dependencies
Testing is easier
```

------------------------------------------------------------------------

# 20. `@Autowired`

`@Autowired` tells Spring to resolve and inject a dependency.

Example:

``` java
@Service
public class OrderService {

    private final PaymentService paymentService;

    @Autowired
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

With a single constructor, the annotation is unnecessary.

# 21. `@Qualifier`

Suppose there are multiple beans of the same type:

``` java
@Bean
public PaymentService stripePaymentService() {
    ...
}

@Bean
public PaymentService razorpayPaymentService() {
    ...
}
```

Spring now has ambiguity.

Use:

``` java
@Qualifier("stripePaymentService")
```

to select the desired bean.

Conceptually:

``` text
PaymentService
      │
      ├── stripePaymentService
      └── razorpayPaymentService
                │
                ▼
           @Qualifier
                │
                ▼
       Select exact bean
```

------------------------------------------------------------------------

# 22. `@Primary`

Another solution to multiple candidates:

``` java
@Primary
@Bean
public PaymentService stripePaymentService() {
    ...
}
```

Now it becomes the default candidate when no qualifier is specified.

Think:

``` text
Multiple beans
     ↓
@Primary
     ↓
Default candidate
```

`@Qualifier` is more explicit.

# 23. Bean Lifecycle

A simplified bean lifecycle is:

``` text
Instantiate object
       ↓
Populate / inject dependencies
       ↓
Aware callbacks (when applicable)
       ↓
BeanFactoryPostProcessor / infrastructure processing
       ↓
BeanPostProcessor - before initialization
       ↓
@PostConstruct
       ↓
InitializingBean
       ↓
Custom init method
       ↓
BeanPostProcessor - after initialization
       ↓
Bean ready
```

For example:

``` java
@PostConstruct
public void init() {
    System.out.println("Initialized");
}
```

runs during bean initialization.

# 24. `BeanFactoryPostProcessor` vs `BeanPostProcessor`

This distinction is frequently useful in interviews.

## `BeanFactoryPostProcessor`

Works primarily with **bean definitions / metadata** before normal bean
instantiation.

Think:

``` text
BeanDefinition
      ↓
BeanFactoryPostProcessor
      ↓
Modified/processed bean metadata
      ↓
Bean creation
```

## `BeanPostProcessor`

Works around the **actual bean instances**.

Think:

``` text
Bean object
    ↓
BeanPostProcessor
    ↓
possibly wrapped/enhanced bean
```

AOP infrastructure heavily relies on post-processing of beans.

# 25. Where AOP Fits Into Startup

Suppose:

``` java
@Service
public class PaymentService {

    @Transactional
    public void pay() {
        // ...
    }
}
```

Spring may expose a proxy instead of the raw target object.

Conceptually:

``` text
Application
    │
    ▼
PaymentService Proxy
    │
    ▼
PaymentService Target
```

When code calls:

``` java
paymentService.pay();
```

the actual flow can be:

``` text
Caller
  ↓
Proxy
  ↓
Transaction interceptor
  ↓
Target.pay()
  ↓
Return
  ↓
Commit / Rollback
```

The same general proxy/interceptor idea is used by features such as:

``` text
@Transactional
@Async
@Cacheable
```

depending on the specific infrastructure.

------------------------------------------------------------------------

# 26. Self-Invocation Gotcha

This is important.

Consider:

``` java
@Service
public class PaymentService {

    @Transactional
    public void pay() {
    }

    public void process() {
        this.pay();
    }
}
```

When:

``` java
process()
```

calls:

``` java
this.pay();
```

the call stays inside the target object.

It does not pass through the Spring proxy.

So the interceptor associated with `@Transactional` may not run for that
self-invocation.

Conceptually:

``` text
External call:

Caller
  ↓
Proxy
  ↓
Target.pay()
  ↓
@Transactional works
```

But:

``` text
Self invocation:

Target.process()
      │
      └── this.pay()
              │
              ▼
        Direct target call
              │
              ▼
        Proxy bypassed
```

A common solution is to move the transactional method into another
Spring bean and call that bean.

# 31. Step 7 --- Application Events

Spring Boot publishes lifecycle events during startup.

A simplified conceptual sequence:

``` text
Starting
   ↓
Environment prepared
   ↓
Context prepared
   ↓
Context loaded
   ↓
Context refreshed
   ↓
Application started
   ↓
Application ready
```

You can listen for:

``` java
@EventListener
public void onReady(ApplicationReadyEvent event) {
    System.out.println("Application is ready");
}
```

`ApplicationReadyEvent` indicates that the application has completed
startup and is ready to serve/use its normal workload.

# 35. `@Bean` vs `@Component`

This is a common interview question.

## `@Component`

You put it on the class:

``` java
@Component
public class EmailService {
}
```

Spring discovers it through component scanning.

``` text
@Component
    ↓
@ComponentScan
    ↓
BeanDefinition
    ↓
Bean
```

## `@Bean`

You put it on a method inside a configuration class:

``` java
@Configuration
public class AppConfig {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}
```

Here you explicitly tell Spring:

> Register the object returned by this method as a Spring bean.

Think:

``` text
@Component
    → Spring discovers the class

@Bean
    → Developer explicitly defines how the bean is created
```

`@Bean` is especially useful for third-party classes that you cannot
annotate.

# 36. `@ConfigurationProperties`

Instead of scattering configuration values:

``` java
@Value("${payment.timeout}")
private int timeout;
```

you can group related configuration:

``` yaml
payment:
  timeout: 5000
  retries: 3
  enabled: true
```

and bind it:

``` java
@ConfigurationProperties(prefix = "payment")
public class PaymentProperties {

    private int timeout;
    private int retries;
    private boolean enabled;

    // getters/setters
}
```

Conceptually:

``` text
application.yml
      ↓
Environment
      ↓
@ConfigurationProperties
      ↓
PaymentProperties bean/object
```

This is often cleaner for larger configuration groups.

### Spring Boot

# 38. Interview Answer --- 30 Seconds

If the interviewer asks:

> "What happens when Spring Boot starts?"

A concise answer:

> `SpringApplication.run()` bootstraps the application. Spring Boot
> determines the application type, prepares the Environment from
> configuration sources, creates the appropriate ApplicationContext,
> processes the `@SpringBootApplication` configuration, performs
> component scanning and auto-configuration, registers bean definitions,
> refreshes the context and creates/initializes required beans with
> dependency injection and applicable post-processors. For web
> applications it starts the embedded server, and finally publishes
> startup/ready events such as `ApplicationReadyEvent`.

# 39. Interview Answer --- If They Ask About `@SpringBootApplication`

Say:

> "`@SpringBootApplication` is a convenience annotation composed of
> `@SpringBootConfiguration`, `@EnableAutoConfiguration`, and
> `@ComponentScan`. `@SpringBootConfiguration` marks the Boot
> configuration class, `@ComponentScan` discovers application
> components, and `@EnableAutoConfiguration` activates conditional Boot
> configurations based on the classpath, environment, and existing
> beans."

# 40. Interview Follow-Up Questions You Should Expect

Once you explain startup, an interviewer can go deeper with:

### Q1. What is `ApplicationContext`?

The Spring IoC container responsible for managing beans, dependencies,
lifecycle, events, environment, and application infrastructure.

### Q2. What is a `BeanDefinition`?

Metadata describing how Spring should create and manage a bean.

### Q3. Does component scanning immediately create beans?

No. It primarily discovers components and registers bean definitions.
Actual bean creation occurs during context initialization, depending on
scope and lazy/eager behavior.

### Q4. What is auto-configuration?

Conditional configuration supplied by Spring Boot that configures
infrastructure based on classpath contents, properties, existing beans,
and other conditions.

### Q5. How does Spring Boot know what to auto-configure?

Through auto-configuration metadata and configuration classes whose
conditions determine whether they should activate.

### Q6. What happens if I define my own `DataSource`?

Auto-configuration commonly uses conditions such as
`@ConditionalOnMissingBean`, so the default configuration backs off when
an appropriate user-defined bean already exists.

### Q7. What is the difference between `BeanFactoryPostProcessor` and `BeanPostProcessor`?

`BeanFactoryPostProcessor` works primarily with bean
definitions/metadata before normal bean instantiation.
`BeanPostProcessor` operates around bean instances and can modify/wrap
them.

### Q8. Where does AOP happen?

Spring's AOP infrastructure can create proxies around eligible beans,
allowing interceptors such as transaction, caching, and async behavior
to execute around method calls.

### Q9. Why doesn't self-invocation trigger `@Transactional`?

Because:

``` java
this.someMethod();
```

is a direct call on the target object and bypasses the Spring proxy.

### Q10. What is the difference between Servlet and Reactive applications?

Servlet applications use the traditional Servlet/Spring MVC stack, while
Reactive applications use Spring WebFlux and a reactive/non-blocking
programming model.

### Q11. Can Spring Boot run without a web server?

Yes. A non-web application can use:

``` java
app.setWebApplicationType(WebApplicationType.NONE);
```

This is useful for workers, Kafka consumers, batch applications, and CLI
programs.
